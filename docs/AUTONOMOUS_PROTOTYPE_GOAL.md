# 자율 프로토타입 개발 목표 — 완전 플레이 가능 프로토타입

> 상태: 저장 완료 / **실행 대기 (구현 미개시)**
> 저장일: 2026-07-31
> 지시자: 사용자
> 대상 브랜치: `agent/phase2-full-prototype` (아직 생성하지 않음)
> 원문 보존: §1 ~ §15는 사용자 지시 원문이며 **편집하지 않는다.**

이 문서는 다음 장시간 자율 개발 실행의 **목표·절차·완료 조건**을 저장소 안에 동결한 것이다.
`docs/` 디렉터리의 다른 문서가 "제품이 무엇인가"를 정의한다면, 이 문서는 **"이번 실행에서
무엇을 어디까지 하고 언제 멈추는가"**를 정의한다.

# 0. 이 문서의 위치와 권한

## 0.1 이 문서가 정하는 것

- 이번 실행의 구현 범위와 제외 범위
- 측정 가능한 완료 조건 (Gate A ~ Gate H)
- Notion·비주얼 레퍼런스 확인 절차
- 안전 상한: **최대 9시간 또는 120개 작업 턴**
- 최종 보고 형식

## 0.2 이 문서가 정하지 않는 것

- Unity 기술 계약 → `docs/TECH_SPEC.md`
- 시각 평가 기준 → `docs/VISUAL_SPEC.md`, `.claude/visual-criteria.md`
- 파일 소유권과 병렬 규칙 → `CLAUDE.md`
- 이미 확정된 설계 결정 → `docs/DECISION_LOG.md`

## 0.3 문서 간 우선순위

**요구사항 축 — "무엇을 만드는가"가 충돌할 때** (§1의 원문 순서를 그대로 적용한다)

1. `docs/DECISION_LOG.md`의 Accepted 결정
2. `docs/CURRENT_PHASE.md`의 현재 범위
3. `docs/MASTER_PRD.md`
4. Notion MASTER PRD와 부록
5. 기존 코드의 현재 동작

이 문서는 위 목록의 **2번을 대체하는 것이 아니라 2번에 반영되어야 한다.** 실행 첫 단계에서
이 문서의 범위를 `CURRENT_PHASE.md`에 갱신하고 `DECISION_LOG.md`에 결정 항목을 남긴다
(부록 B-1). 그 전까지 `CURRENT_PHASE.md`는 여전히 "Phase 1 + 1층 Hero Slice"를 Active로
선언하고 있으며, §3의 제외 항목(10층, 승객 4종, 부품 4종)이 이 문서의 Gate B·C와 정면
충돌한다. 절차를 건너뛰고 구현부터 시작하지 않는다.

**기술·시각 축 — "어떻게 만들어야 유효한가"**

`docs/TECH_SPEC.md`와 `docs/VISUAL_SPEC.md`는 위 순위표의 어느 단계에도 종속되지 않는
**직교 제약**이다. 요구사항이 어디서 왔든 다음이 성립해야 한다.

- 이 문서가 TECH_SPEC/VISUAL_SPEC보다 **더 구체적이고 더 엄격한** 경우 → 이 문서를 따르고,
  해당 내용을 VISUAL_SPEC 또는 신설 `DEVICE_DESIGN_SPEC.md`로 동결한다.
- 이 문서가 TECH_SPEC/VISUAL_SPEC의 제약을 **완화하는** 것으로 읽히는 경우
  → TECH_SPEC/VISUAL_SPEC이 우선한다. 완화는 `DECISION_LOG.md` 항목 없이 성립하지 않는다.

**Notion 취급** — `D-20260730-01`이 확정한 절차를 유지한다. Notion은 자동 적용되지 않는다.
Notion에서 발견된 누락 요구사항은 **구현 전에 저장소 문서로 동결한 뒤** 구현한다.

## 0.4 Gate 이름 주의

`docs/CURRENT_PHASE.md` §5에 이미 **다른 의미의 Gate A~D**가 존재하며 커밋 `0125b92`에서
전부 통과로 판정되었다. 이 문서의 Gate A~H는 그것과 무관한 별개 체계다. 혼동을 막기 위해
보고·커밋·로그에서는 이 문서의 게이트를 **`P2-Gate A` ~ `P2-Gate H`**로 표기하고,
기존 것은 `Phase1-Gate A~D`로 표기한다.

ultracode Dynamic Workflow를 사용해 `dlsaa86/Upandup_DDD`의 다음 완전한 플레이 가능 프로토타입 마일스톤을 장시간 자율 구현하고 검증하라.

Unity Editor는 실행 중이며 Unity MCP를 사용할 수 있다. 사용자에게 사소한 판단을 반복해서 묻지 말고, 교체 가능한 기본값을 선택해 기록하면서 작업을 계속하라.

최대 9시간 또는 120개 작업 턴을 안전 상한으로 사용한다. 시간을 채우기 위한 불필요한 기능 추가는 금지한다. 아래의 모든 완료 조건이 먼저 충족되면 증거를 제출하고 종료한다. 조건이 충족되지 않았다면 중간 요약만 하고 멈추지 말고 다음 미완료 Gate를 계속 수행한다.

저장소의 문서는 구현 중 동결된 기준이며, Notion은 상세 기획과 비주얼 원본이다.

Notion에서 저장소 문서에 누락된 중요한 내용이 발견되면 구현 전에 저장소 문서로 동결한다.

필요에 따라 다음 문서를 생성하거나 갱신한다.

* `docs/VISUAL_BIBLE.md`
* `docs/DEVICE_DESIGN_SPEC.md`
* `docs/SYMBOL_DESIGN_SPEC.md`
* `docs/ASSET_PIPELINE.md`
* `docs/runtime/NotionSyncReport.md`

`NotionSyncReport.md`에는 다음을 기록한다.

* Notion에서 확인한 페이지
* 저장소에 이미 반영된 내용
* 새롭게 발견된 요구사항
* 충돌한 내용과 적용한 우선순위
* 이미지나 첨부 자료 중 읽지 못한 항목
* 사용자 승인이 필요한 항목

Notion 또는 이미지 접근이 일부 실패해도 전체 작업을 중단하지 않는다. 접근 가능한 자료와 저장소 기준으로 진행하고, 확인하지 못한 내용만 명확히 기록한다.

# 2. 현재 상태 감사

이미 완료된 Phase 1과 1층 Hero Slice를 처음부터 다시 작성하지 않는다.

먼저 현재 저장소를 조사하고 다음 파일을 생성하거나 최신화한다.

* `docs/runtime/GapAnalysis.md`
* `docs/runtime/VisualGapAnalysis.md`
* `docs/runtime/ImplementationPlan.md`
* `docs/runtime/ProgressLog.md`

현재 코드, 씬, 데이터, 테스트, 캡처 하네스를 PRD 요구사항과 매핑한다.

모든 요구사항을 다음 중 하나로 분류한다.

* 완료
* 부분 완료
* 미완료
* 현재 Phase 제외
* 사용자 승인 필요
* 환경 제약으로 차단

기존에 정상 작동하고 테스트된 시스템은 근거 없이 재작성하지 않는다. 최소 변경으로 요구사항을 연결하고 보강한다.

# 3. 이번 장기 실행의 구현 목표

이번 목표는 기존 Hero Slice를 보존하면서 다음을 하나의 플레이 가능한 프로토타입 흐름으로 연결하는 것이다.

## 게임 진행

* 1인칭 엘리베이터 내부 이동과 상호작용
* 1층부터 10층까지 연속 진행
* 층 시작 계약 또는 위험 선택
* 층당 최대 스핀 수와 상승 조건
* 요구 전력 달성 후 전력 확정 또는 과수확 선택
* 실패, 사고, 완주 결과
* 고정 시드와 특정 층·스핀 단독 재현

## 룰렛 코어

* 기존 결정론적 3×3 자동 룰렛 보존
* 정상 영혼, 흡수체, 증식체
* 같은 저항체 3개 이상 기본 정화
* 가로·세로·대각선 직선 판정
* 직교 연결 4개 이상 판정
* 제거, 재충전, 캐스케이드
* 최대 캐스케이드 20
* 무한 루프와 진행 불가 상태 방지
* 정화 원인과 캐스케이드 원인의 시각적 판독

## 승객·부품·적재

* 최소 4종 이상의 승객과 부품 콘텐츠
* 승객과 부품이 메뉴 아이콘으로만 존재하지 않고 엘리베이터 안에 실제로 배치됨
* 총중량, 허용 중량, 과적 상태
* 적재량에 따른 요구 전력 또는 위험 변화
* 승객과 부품이 룰렛 확률, 점수, 정화, 캐스케이드, 잔류 위험 중 일부를 실제로 변경
* 최소 두 개의 명확히 다른 빌드 또는 운용 전략
* 승객의 목적지, 승차, 하차 또는 보상 흐름
* 최대 적재 상태에서도 플레이 이동 공간과 핵심 장치 접근성 유지

## 위험과 사고

* Stable
* Warning
* Critical
* Collapse 또는 Accident

각 상태는 단순 UI 문구가 아니라 다음 공간 채널을 조합해 표현한다.

* 조명
* 저주파와 사이렌
* 금속 응력음
* 기계 진동
* 승객 불안 반응
* 증기 또는 제한된 입자
* 순간적인 엘리베이터 움직임
* 실패 직전의 정적 또는 긴장 변화

판독성을 파괴하는 과도한 화면 흔들림, 섬광, 안개, 파티클은 금지한다.

사고 기록기는 최소한 다음을 제공한다.

* 런 시드
* 실패 층
* 실패 직전 스핀
* 선택한 계약
* 승객과 부품
* 무게
* 전력
* 위험 상태
* 과수확 횟수
* 잔류 저항
* 직접적인 실패 원인

# 4. 비주얼 방향

이번 작업은 기능만 연결하는 것이 아니라 게임의 그래픽 분위기와 핵심 장치 디자인도 함께 검증해야 한다.

## 전체 그래픽 방향

* 낡은 1960년대 산업용 화물 엘리베이터
* PS1 및 초기 PS2 생존 호러
* 단순하고 각진 로우폴리 지오메트리
* 큰 실루엣과 눈에 띄는 폴리곤 면
* 저해상도 손그림 픽셀 텍스처
* 탁하고 제한된 색상
* 차가운 회녹색 그림자와 바랜 산업용 색
* 단순한 Gouraud 또는 플랫 셰이딩
* 제한적인 국소 조명과 빠른 감쇠
* 좁고 높고 기능적인 공간
* 실제 1인칭 게임에서 읽히는 크기와 배치

다음 방향은 금지한다.

* 현대적 PBR 그래픽
* 사실적인 AAA 산업 시설
* 스팀펑크 장식
* 카지노 슬롯머신 이미지
* 황동 장식과 불필요한 톱니
* 과도한 파이프와 계기판
* 이유 없는 기계장치 추가
* 현대적 홀로그램 UI
* 깨끗하고 대칭적인 쇼룸 구성
* 작은 디테일로 실루엣을 흐리는 디자인
* 그래픽 분위기만 있고 실제 플레이가 불가능한 공간

## 엘리베이터 공간

반드시 확인하고 수정한다.

* 좁고 높은 직사각형 구조
* 녹슨 철판 바닥
* 리벳과 패널이 드러난 벽
* 접이식 가위문 또는 무거운 산업용 문
* 어두운 외부 복도
* 약한 천장 조명
* 출입구 위 현재 층수 표시
* 승객과 화물을 위한 비어 있는 중앙 공간
* 플레이어가 핵심 장치를 한눈에 확인할 수 있는 1인칭 비율
* 최대 적재 상태에서도 이동과 상호작용 가능

## 세 통관 영혼 수확 장치

다음 대응 관계가 정면에서 즉시 읽혀야 한다.

* 세 개의 수직 통관
* 각 통관과 3×3 결과판의 한 열
* 각 결과의 판독 위치
* 전력 계기판
* 일반 실행 레버
* 과수확 레버

기계는 다음 성격을 가져야 한다.

* 오래되고 위험함
* 각지고 단순함
* 모듈식 프레임
* 향후 통관 또는 기능 모듈 확장 가능
* 파이프와 케이블은 기능적 연결을 설명할 때만 사용
* 작은 장식보다 큰 구조와 기능 대응을 우선
* 플레이어 시점에서 너무 크거나 너무 작지 않음
* 승객과 화물 공간을 침범하지 않음

## 실행 레버

* 사람의 손 높이에서 한 손으로 조작 가능한 크기
* 통상적인 스핀 실행 장치로 명확히 읽힘
* 과수확 레버와 형태, 크기, 위치가 구분됨
* 다른 장치와 혼동되지 않음

## 과수확 레버

* 일반 실행 레버보다 크고 무거움
* 보호 덮개 또는 물리적 잠금 구조
* 요구 전력 달성 전에는 실제로 잠겨 보임
* 잠긴 상태에서 손잡이에 접근할 수 없어야 함
* 해제 순간 조명, 음향, 진동, 걸쇠 반응이 집중됨
* 붉은색 하나에만 의존하지 않음
* 게임의 대표적인 위험 선택 장면으로 보임

## 심볼

정상 영혼, 흡수체, 증식체는 색상 외에도 최소 세 항목이 달라야 한다.

* 움직임과 맥동

* 사운드

* 피벗
* 상태별 변화
* 확장 가능한 연결부

최종 아트가 준비되지 않은 항목은 교체 가능한 로우폴리 플레이스홀더로 구현한다. 플레이스홀더라도 형태, 비율, 동선과 기능 판독은 실제 목표와 일치해야 한다.

# 10. 실패 대응

* 동일 오류를 같은 방식으로 세 번 이상 수정하지 않는다.
* 반복 실패 시 최소 재현 테스트를 만든다.
* 해결되지 않는 비차단 기능은 인터페이스 뒤로 격리하고 계속 진행한다.
* 컴파일이나 핵심 테스트가 깨진 상태에서 새 기능을 추가하지 않는다.
* 임시 예외 처리로 원인을 숨기지 않는다.
* Unity 버전, URP, 패키지 버전을 임의로 변경하지 않는다.
* 외부 유료 에셋이나 서비스를 사용하지 않는다.
* 씬 또는 직렬화 에셋 손상이 의심되면 마지막 정상 커밋으로 복구한다.
* Unity MCP가 일시적으로 실패하면 로그, 메뉴 명령, 테스트 러너 등 대체 경로를 시도한다.
* 환경 제약은 기능 실패와 구분해서 기록한다.

# 13. 완료 Gate

다음 조건이 모두 증거와 함께 충족될 때만 목표 완료를 선언한다.

## Gate A — 명세

* 저장소와 Notion의 요구사항 감사 완료
* 주요 누락 사항이 저장소 문서에 동결됨
* 충돌과 미확인 자료가 기록됨
* 구현 범위와 제외 범위가 명확함

## Gate B — 게임 진행

* 디버그 조작 없이 1층부터 10층까지 연속 진행 가능
* 계약, 스핀, 정화, 캐스케이드, 전력, 확정 또는 과수확, 상승이 연결됨
* 완주 또는 사고 결과가 정상적으로 종료됨
* 진행 불가 상태 없음

## Gate C — 빌드와 적재

* 최소 4종 이상의 승객·부품
* 최소 두 개의 다른 빌드 전략
* 무게와 적재 제한이 실제 선택에 영향
* 승객과 부품이 룰렛 또는 위험 규칙을 실제로 변경
* 승차·하차·획득·배치 흐름 작동
* 최대 적재 상태에서도 플레이 가능

## Gate D — 결정론과 테스트

* Unity 컴파일 오류 0
* 핵심 EditMode 테스트 전부 통과
* 핵심 PlayMode 테스트 전부 통과
* 동일 시드 동일 결과
* 서로 다른 고정 시드 최소 3개 검증
* 10층 연속 런 최소 3회 검증
* 캐스케이드 무한 루프 없음
* 캐스케이드 20 하드 캡 작동

## Gate E — 비주얼과 장치

* 엘리베이터가 좁고 높은 산업용 화물 공간으로 읽힘
* PS1·초기 PS2 로우폴리 호러 방향 유지
* 현대적 PBR 또는 스팀펑크·카지노 방향이 아님
* 승객과 화물 공간 보존
* 세 통관과 3×3 결과 대응이 명확
* 실행 레버와 과수확 레버 즉시 구분
* 과수확 잠금 구조가 물리적으로 이해 가능
* 세 심볼을 색상 없이 실루엣으로 구분 가능
* 불필요한 기계와 콘솔이 없음
* Stable·Warning·Critical·Collapse가 동일 공간의 상태 변화로 보임
* 직전 승인 캡처보다 명백히 나빠지지 않음

## Gate F — 위험과 사고

* 네 위험 상태가 실제 게임 상태와 동기화
* 조명·음향·진동·승객 반응이 상태에 따라 변화
* 과수확이 위험과 보상을 실제로 변경
* 사고 기록기가 실패 원인과 런 데이터를 정확히 표시
* 단순 암전이나 즉사만으로 실패 정보를 숨기지 않음

## Gate G — 성능과 증거

* 필수 캡처 세트 생성
* CPU와 GC 측정
* 최대 적재와 Critical 상태 측정
* 주요 프레임 스파이크 조사
* 게임 코드 비용과 에디터 비용 구분
* 성능 미달 또는 기준 하드웨어 미확정 사항을 숨기지 않음
* `docs/runtime/ProgressLog.md`에 측정값과 실패 이력 기록

## Gate H — 독립 재검토

첫 통과 뒤 별도의 QA·비주얼·성능 작업자가 독립적인 두 번째 검토를 수행한다.

다음을 다시 확인한다.

* PRD 누락
* 테스트 사각지대
* 10층 진행 막힘
* 씬 참조 손상
* 심볼 혼동
* 장치 크기와 동선
* 불필요한 기계 추가
* 과수확 레버의 잠금·해제 판독
* GC와 프레임 스파이크
* 직전 승인 빌드 대비 시각적 퇴보

발견된 문제를 수정하고 관련 Gate를 다시 검증한다.

# 14. 자율 진행 규칙

사소한 모호성 때문에 사용자에게 질문하거나 작업을 종료하지 않는다.

다음 형식으로 `docs/ASSUMPTION_LOG.md`에 기록하고 진행한다.

* 선택한 기본값
* 판단 근거
* 영향을 받는 시스템
* 관련 파일 또는 데이터 위치
* 나중에 교체하는 방법

다만 되돌리기 어렵고 게임의 정체성을 크게 바꾸는 결정은 최종 확정하지 않는다. 교체 가능한 구조와 프리셋으로 남긴다.

"현재 Phase를 완료했다"는 이유만으로 멈추지 않는다. 이번 명령의 Gate A~H가 완료 기준이다.

하나의 작업자가 완료를 주장하더라도 독립 evaluator가 증거를 확인해 미완료로 판정하면 다음 작업 턴을 계속한다.

# 부록 D — 야간 실행·크래시 복구 규칙

> 추가일: 2026-07-31
> 근거: 사용자 지시 (무인 야간 실행 대비)
> 관련 도구: `tools/unity-watchdog.ps1`, `.claude/hooks/unity-preflight.sh`

무인 실행에서 가장 비싼 실패는 기능 실패가 아니라 **아무도 없는 사이에 멈춰 있는 것**이다.
이 부록은 그 시간을 회수하기 위한 규칙이다.

## D-1. 복구 가능 마일스톤

각 복구 가능한 마일스톤마다 다음을 수행한다.

1. Play Mode를 종료한다.
2. 열린 씬과 수정된 에셋을 저장한다.
3. Unity 컴파일 상태를 확인한다.
4. 관련 테스트를 실행한다.
5. `docs/runtime/ProgressLog.md`에 현재 상태와 다음 시작점을 기록한다.
6. 복구 가능한 로컬 커밋을 생성한다.

이 순서에는 이유가 있다. Unity가 죽으면 **에디터 메모리에만 있던 것은 전부 사라진다.**
저장하지 않은 씬 변경, 커밋하지 않은 진행, 기록하지 않은 판단이 그렇다. 크래시 이후
복구의 출발점은 언제나 "마지막으로 디스크에 쓴 것"이므로, 마일스톤마다 디스크에
쓰지 않으면 복구 지점 자체가 존재하지 않는다.

Unity Console에 동일 오류가 반복 출력되는 상태를 방치하지 않는다. 짧은 시간 안에 같은
오류가 반복되면 추가 구현을 중단하고 로그 폭주의 원인을 먼저 제거한다. 초당 수십 줄을
쓰는 콘솔은 그 자체로 디스크와 에디터를 잡아먹어 크래시 원인이 된다.

## D-2. Unity MCP 연속 실패 대응

Unity MCP 호출이 연속 세 번 실패하면 같은 호출을 반복하지 말고 다음을 수행한다.

1. Unity 프로세스가 실행 중인지 확인한다.
2. Unity watchdog 로그와 최신 Editor 로그를 확인한다.
3. Unity가 재시작 중이면 프로젝트 로딩과 컴파일이 완료될 때까지 기다린다.
4. MCP 연결을 다시 확인한다.
5. 최소 컴파일 및 씬 로드 검증을 수행한다.
6. `ProgressLog.md`의 마지막 정상 마일스톤부터 작업을 재개한다.

`.claude/hooks/unity-preflight.sh`가 **감지**를 담당한다. 이 훅은 모든 `mcp__unity-mcp__*`
호출 앞에서 `Library/EditorInstance.json`의 PID가 실제로 살아 있는지 확인하고, 죽어 있으면
즉시 거부한다. 따라서 에디터가 죽었을 때 120초 툴 타임아웃을 기다리는 일은 없고, 대신
**거부 메시지가 곧 진단 결과**다. 그 메시지를 보면 위 1번은 이미 확인된 것이다.

`tools/unity-watchdog.ps1`가 **복구**를 담당한다. 둘은 짝이며 하나만으로는 부족하다.
훅만 있으면 죽은 채로 밤을 보내고, watchdog만 있으면 재시작 중에 MCP 호출을 계속 던진다.

## D-3. 재시작 이후의 상태 가정 금지

Unity 재시작 후에는 이전 Editor 메모리 상태나 저장되지 않은 씬 상태가 보존되었다고
가정하지 않는다. 저장된 파일과 마지막 정상 로컬 커밋을 기준으로 현재 상태를 다시 확인한다.

특히 다음을 다시 확인한다.

- `git status --porcelain` — 재시작 전 인지하던 것과 다른 변경이 있는지
- Unity 컴파일 오류 0
- 마지막 `ProgressLog.md` 항목이 실제 디스크 상태와 일치하는지

로그는 프로젝트 상대 경로에 있다.

```text
Logs/Editor.log                    현재 실행 중인 에디터
Logs/UnityWatchdog/watchdog.log    watchdog 의 감지·재실행 이력
Logs/UnityWatchdog/Editor-*.log    재실행 직전에 보존한 크래시 로그
```

`%LOCALAPPDATA%\Unity\Editor\Editor.log`가 아니다. watchdog은 재실행 직전에
`Logs/Editor.log`를 타임스탬프 붙여 복사해 둔다. Unity가 시작할 때 그 파일을 덮어쓰므로,
복사하지 않으면 크래시 원인이 사라지기 때문이다.

크래시 로그에서 보통 다음을 확인한다.

- `Crash`, `Fatal`, `Access violation`, `Stack overflow`
- `Out of memory`
- 반복되는 동일 예외
- 패키지 또는 MCP 관련 오류
- 마지막으로 실행한 테스트나 에디터 명령

## D-4. 장애를 완료로 바꾸지 않는다

Unity 또는 MCP 장애가 발생했다는 이유만으로 전체 목표를 완료 처리하지 않는다.
자동 복구가 가능하면 복구 후 계속하고, 복구할 수 없는 경우에만 다음을 기록하고 멈춘다.

- 정확한 로그 경로
- 마지막 정상 커밋
- 실패한 작업과 재현 절차
- 재개 절차

이는 §14의 "현재 Phase를 완료했다는 이유만으로 멈추지 않는다"와 같은 규칙의 뒷면이다.
**환경 장애는 미완료이지 완료가 아니다.** §15 보고의 "환경 제약" 항목에 기록한다.

## D-5. watchdog 자동 재실행의 한계

watchdog이 복구할 수 있는 것과 없는 것을 구분한다. 이것을 구분하지 않으면 복구되지 않은
밤을 복구된 것으로 착각한다.

| 상황 | 자동 복구 |
|---|---|
| Unity 단독 종료·크래시 | 가능 |
| 터미널 종료 | Claude 백그라운드 세션이면 가능 |
| 일시적 MCP 파이프 단절 | 대체로 가능 (재연결) |
| OS 잠자기·최대 절전 | **불가** — 사전에 해제해 둘 것 |
| 강제 재부팅, 정전 | **불가** |
| GPU 드라이버 장애 | **불가한 경우가 많다** |
| 같은 지점에서 반복 크래시 | **의도적으로 중단한다** (아래) |

watchdog은 시간창(기본 60분) 안에서 재실행 횟수가 상한(기본 5회)을 넘으면 자동 재실행을
멈추고 대기한다. 같은 지점에서 계속 죽는 에디터를 1분마다 다시 띄우는 것은 복구가 아니라
로그와 디스크를 태우는 일이고, 원인을 덮어 다음 날 진단을 더 어렵게 만들기 때문이다.
`watchdog.log`에 `크래시 루프 의심`이 남아 있으면 그 밤의 결과는 신뢰하지 않는다.

## D-6. 야간 실행 전 점검

무인 실행을 시작하기 전에 다음을 확인한다. **watchdog을 켜기만 하고 검증하지 않은 상태로
밤을 넘기지 않는다** — Unity는 재실행됐는데 MCP가 붙지 않으면 복구되지 않은 것과 같다.

1. 전원 연결, 잠자기·최대 절전 해제 (`powercfg /change standby-timeout-ac 0`)
2. `git status --porcelain` 정리, `agent/` 브랜치 위에 있는지 확인
3. Unity 컴파일 오류 0, 자체 테스트 통과 (부록 B-4)
4. watchdog 실행
5. **Unity 강제 종료 후 자동 재실행 확인**
6. **재실행 이후 Unity MCP 호출 성공 확인**
7. Claude 백그라운드 세션 확인

5번과 6번을 건너뛰면 나머지는 의미가 없다.
