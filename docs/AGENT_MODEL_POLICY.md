# 에이전트 모델 역할 및 실행 정책

> 상태: 저장소 운영 규칙  
> 적용 대상: Claude Opus 5, OpenAI Sol 및 이들을 오케스트레이션하는 상위 에이전트  
> 제품 요구사항과 충돌할 경우 `MASTER_PRD.md` → `TECH_SPEC.md` → `CURRENT_PHASE.md`가 우선한다.

이 문서는 모델의 우열을 선언하는 문서가 아니다. 각 모델이 강점을 발휘하도록 **구현과 검증의 책임을 분리**하고, 같은 결과를 스스로 구현하고 승인하는 구조를 방지하기 위한 운영 계약이다.

---

# 1. 기본 역할

## 1.1 Claude Opus 5 — Lead / Integration Owner

Opus 5는 기본적으로 게임 구현과 통합의 주 소유자다.

주요 책임:

- PRD를 실제 플레이 경험과 구현 순서로 변환
- Unity 씬, 프리팹, 조명, 재질, 카메라, 포스트프로세싱의 단일 통합 소유
- 게임플레이 로직과 공간 연출의 연결
- 여러 시스템이 결합된 대표 장면의 순차 개선
- 구현 전 요구사항 매핑과 계획 작성
- Sol 감사 결과의 우선순위 판단과 수정 반영
- 테스트·캡처·성능 증거가 갖춰진 상태로 검토 요청

Opus 5가 우선 소유하는 작업 예시:

- 엘리베이터 공간 구성과 1인칭 동선
- 룰렛 장치와 레버의 상호작용 구조
- Stable·Warning·Critical 공간 연출
- 과수확 레버 해제부터 폭주까지의 대표 시퀀스
- 카메라, 조명, 재질, 사운드, 진동을 묶는 감각적 피드백
- PRD의 감정 곡선과 노스스타를 실제 플레이로 구현하는 작업

Opus 5는 자신의 구현을 최종 승인하지 않는다.

## 1.2 OpenAI Sol — Audit / Verification Owner

Sol은 기본적으로 구현 결과를 독립적으로 감사하고, 검증 가능한 엔지니어링 문제를 찾는 역할이다.

주요 책임:

- 코드베이스와 상태 전이 감사
- 요구사항 누락, 죽은 경로, 이중 구현, 연결되지 않은 이벤트 탐지
- 결정론, 테스트 커버리지, 재현 절차 검증
- GC, 프레임타임, 첫 사용 스파이크, 빌드 안정성 분석
- 구현자의 주장과 실제 코드·씬·캡처·로그 간 불일치 탐지
- 회귀 가능성과 구조적 위험 보고
- 검토 결과를 심각도와 재현 절차가 있는 형태로 전달

Sol이 우선 소유하는 작업 예시:

- 전체 코드 감사와 상태 전이 버그 탐색
- EditMode·PlayMode 테스트 누락 조사
- 결정론적 시드와 재현 가능성 검증
- 프레임 할당과 성능 병목 분석
- 씬 참조 단절, 미구독 이벤트, 덮어써지는 상태 탐지
- 빌드 설정과 패키지 재현성 확인
- Opus 구현 결과의 독립 코드 리뷰

Sol의 기본 감사 작업은 **읽기 전용**이다. 수정이 필요한 경우 먼저 감사 보고를 완료하고, 별도 수정 작업으로 전환한다.

# 2. 역할은 모델 이름보다 작업 계약이 우선한다

- 오케스트레이터가 역할을 명시했다면 그 역할을 따른다.
- 모델이 자신의 정확한 제품명 또는 실행 역할을 확인할 수 없으면 추측하지 않는다.
- 역할이 명시되지 않은 Claude Opus 세션은 `Lead / Integration Owner`로 시작한다.
- 역할이 명시되지 않은 OpenAI Sol 세션은 `Audit / Verification Owner`로 시작한다.
- 다른 모델은 작업 지시에서 지정된 역할을 따른다. 역할이 없으면 코드를 수정하기 전에 현재 세션의 소유 범위를 계획에 명시한다.

모델 이름만으로 모든 권한이 자동 부여되는 것은 아니다. `CLAUDE.md`의 경로 소유권, 단일 씬 소유자, 브랜치 규칙은 항상 적용된다.

# 3. 표준 실행 순서

## 3.1 구현 패스 — Opus 5

1. `CLAUDE.md`와 문서 우선순위를 읽는다.
2. 현재 코드를 요구사항과 매핑한다.
3. 이번 패스의 **단일 품질 목표**를 정한다.
4. 수정 경로와 단일 소유 영역을 명시한다.
5. 구현한다.
6. 컴파일과 자동 테스트를 실행한다.
7. 실제 플레이 흐름으로 검증한다.
8. 화면 변경이면 고정 시드·고정 카메라 캡처를 생성한다.
9. 성능 영향을 측정한다.
10. 구현 주장, 변경 파일, 테스트, 시드, 캡처, 성능, 남은 위험을 검토 패키지로 남긴다.
11. Sol 감사 전에는 최종 완료로 선언하지 않는다.

## 3.2 감사 패스 — Sol

1. 구현자의 설명을 사실로 가정하지 않는다.
2. 관련 PRD, TECH SPEC, CURRENT PHASE, 시각 기준을 직접 확인한다.
3. diff와 변경되지 않은 인접 코드를 함께 검사한다.
4. 테스트가 요구사항을 실제로 증명하는지 확인한다.
5. 가능하면 동일 시드와 동일 플레이 흐름을 재현한다.
6. 화면 변경은 캡처와 런타임 동작을 코드와 별도로 평가한다.
7. 성능 수치는 평균뿐 아니라 p50, p95, p99, 최악 프레임과 첫 사용 스파이크를 확인한다.
8. 발견 사항을 `BLOCKER`, `HIGH`, `MEDIUM`, `LOW`로 분류한다.
9. 각 발견 사항에 근거 파일, 영향, 재현 절차, 기대 결과를 기록한다.
10. 문제가 없을 때도 검사 범위와 확인하지 못한 항목을 명시한다.

## 3.3 수정 패스 — Opus 5

- Sol 발견 사항을 심각도 순으로 처리한다.
- 증상만 가리는 대신 소유권 충돌, 이중 상태, 데이터 흐름 단절 같은 근본 원인을 우선한다.
- 수정 후 전체 관련 검증을 다시 실행한다.
- 감사와 무관한 신규 기능을 같은 수정 패스에 섞지 않는다.

## 3.4 재감사 — Sol

- 수정된 항목만 보지 말고 인접 회귀를 다시 확인한다.
- `BLOCKER`와 `HIGH`가 남아 있으면 완료를 승인하지 않는다.
- 시각적 완성도는 코드 테스트 통과만으로 승인하지 않는다.

# 5. 병렬화 규칙

병렬 작업은 독립 경로와 독립 결과가 있을 때만 허용한다.

병렬 가능:

- 순수 C# 로직과 별도 테스트
- 텔레메트리와 에디터 도구
- 코드 감사와 레퍼런스 분석
- 서로 다른 경로의 독립 에셋 초안

순차 처리:

- `*.unity`, `*.prefab`, `*.mat`, `*.asset`
- 조명, 카메라, 포스트프로세싱
- 전체 아트 디렉션
- Stable → Critical 전환처럼 여러 감각 채널이 결합된 시스템
- 과수확 대표 장면

여러 에이전트를 사용한다는 이유만으로 팬아웃하지 않는다. 결합된 화면 문제는 하나의 통합 소유자가 순차적으로 해결한다.

# 6. 완료와 승인 규칙

다음 조건을 만족하지 않으면 구현 완료로 선언하지 않는다.

- 관련 자동 테스트 통과
- 실제 플레이 경로 통과
- 동일 시드 재현 가능
- 치명적 콘솔 오류 없음
- 화면 변경 시 고정 캡처와 직전 승인 빌드 대비 회귀 확인
- 성능 영향 기록
- Sol 독립 감사에서 미해결 `BLOCKER` 또는 `HIGH` 없음
- 미검증, 환경 제약, 사용자 승인 대기 항목을 명확히 분리

Sol의 승인은 제품 방향이나 최종 미학을 대신 결정하지 않는다. 색, 최종 재질, 공포 강도, 캐릭터 외형 등 승인 대기 항목은 사용자 선택 대상으로 남긴다.

```text
## 확인하지 못한 항목

## 판정
- 승인 / 조건부 승인 / 수정 필요
```

# 8. 금지 사항

- Opus가 구현 후 자신의 평가만으로 완료 선언
- Sol이 감사와 대규모 수정 작업을 한 패스에서 혼합
- 테스트 통과를 시각 품질 통과로 간주
- 평균 FPS 하나만으로 성능 통과 선언
- 여러 에이전트가 같은 Unity 씬 또는 머티리얼을 동시에 수정
- 검토를 쉽게 만들기 위해 실패 테스트를 삭제하거나 기준을 완화
- 감사 발견 사항을 해결하지 않은 채 신규 기능으로 범위를 확장

핵심 운영 원칙은 다음 한 문장이다.

> **Opus 5가 게임 경험을 구현하고 통합하며, Sol이 그 구현이 실제 요구사항·코드·성능·증거와 일치하는지 독립적으로 감사한다.**
