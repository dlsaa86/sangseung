# 측정 구멍 — 게이트가 다른 게임을 재고 있었다

> 작성: 2026-08-07 야간 자율 세션
> 발단: 카탈로그에 품목을 하나 더했는데 `sweep 20000` 이 **비트 단위로 동일**했다

---

## 1. 무엇이 사실인가

`Assets/Editor/BalanceSweep.cs` 의 세 런 루프가 전부 이렇게 돼 있었다.

```csharp
if (f.Phase == FloorPhase.Boarding && !run.FinishBoarding()) break;
```

`FinishBoarding()` 은 **문을 닫고 넘어간다** — 제시를 비우고 다음 단계로 간다
(`FloorSession.cs:336`). 즉 스윕의 모든 런이 **적재 0개**로 돌았다.

그래서 `docs/runtime/FUN_CRITERIA.md` 의 모든 대역 — 구간별 클리어율, 층별 방문률,
3연쇄 비율, 정화 발생률, 과수확 선택률, 부분 실패 대역 — 이 **빌드가 하나도 없는
게임**에 대한 판정이었다.

노션 `GAMEPLAY CORE` 로 옮기면 이렇게 된다.

| CORE 절 | 요구 | 이 게이트가 잰 것 |
|---|---|---|
| §3.2 좋은 선택이 결과를 바꾸는 체감 | 승객·부품이 결과를 바꾼다 | **아무것도 안 실린 판** |
| §3.3 자동 연쇄의 폭발 | 빌드가 연쇄를 만든다 | 빌드 없는 연쇄 |
| §6 빌드 시스템 전체 | 4명·3부품·시너지 | 측정 대상 아님 |
| §7 강한 빌드는 더 큰 위험도 부른다 | 이득과 대가가 함께 | 이득도 대가도 없음 |

## 2. 어떻게 드러났나

셋이 같은 하나를 가리켰다.

1. **카탈로그를 15종으로 늘렸는데 스윕이 안 움직였다.** 14종일 때와 같은 값을 낼
   방법은 하나뿐이다.
2. **2026-08-06 자체 검증 실패 7건 중 하나가 이미 이렇게 적혀 있었다** —
   「적재 무게가 다음 층으로 이어진다 — **런 내내 아무것도 실리지 않음**」.
   그 실패는 「다른 세션 소유」로 분류돼 세 세션 동안 넘어갔다.
3. **`BuildLoadPolicy` 의 호출자가 측정 경로에 0곳이었다.** 그 클래스 주석은
   「하네스와 헤드리스 테스트가 **같은 것을** 쓴다」고 스스로 적어 두고 있다.
   `CurriculumCoverageProbe` 조차 `TakeBuildOffer(0)` — 번호가 작은 것 —
   을 부르지 그 정책을 부르지 않는다.

**이 저장소가 같은 모양을 만난 것이 이번이 세 번째다.**

| 사례 | 만들어진 것 | 호출자 |
|---|---|---|
| `BuildEffectKind.MultiplePatterns` | 규칙은 구현됨 | 켜는 품목 **0개** |
| `OverharvestSnapshot.IsUnlocked` 외 | 프로파일에 값 있음 | **0곳** (「값을 바꿔도 게임이 그대로인 정확한 원인」) |
| **`BuildLoadPolicy.PickIndex`** | 정본 규칙 | 측정 경로 **0곳** ← 이번 |

세 번 다 「만들어졌는데 아무도 안 쓴다」이고, 세 번 다 **그 사실을 아무것도
출력하지 않았다.** 그래서 발견이 우연에 의존했다.

## 3. 고친 것

`BalanceSweep.RunBoarding()` 을 넣고 세 지점을 그리로 돌렸다.
고르는 규칙은 새로 쓰지 않았다 — `BuildLoadPolicy.PickIndex` 를 부른다.

`BalanceSweep.BoardBuilds = false` 로 두면 옛 판정과 비트 단위로 같다.
헤드리스에서는 `dotnet run -- sweepnoload 20000` 으로 옛 값을 다시 뽑을 수 있다.

시드 20000~39999 · 기대값 정책.

### 층별 — 단조성이 깨져 있다

| 층 | 방문률 | 클리어율 | 가르치는 것 |
|---:|---:|---:|---|
| 7 | 83.7% | 95.1% | 계약 비교 |
| **8** | 79.6% | **97.6%** | **적재 압박** ← 후반에서 가장 쉽다 |

`FUN_CRITERIA` §1 실패 조건 2(「곡선이 단조 감소하지 않는다」)에 걸린다.
그리고 하필 **무게의 대가를 가르치는 층**이 그렇다.

## 5. 다섯 실패가 한 뿌리다

전부 「**적재가 순수 이득**」의 다른 얼굴이다.

- 빌드가 붙으면 완주율이 45.6 → 71.4% 로 오른다. 대가가 그만큼 안 물린다.
- 빌드가 연쇄를 만들어 3연쇄가 23.1% — 「예상 밖」이 아니라 기본값이다.
- 산출이 커지니 정산보다 계속 도는 쪽이 78.5% 에서 옳다 — 멈출 이유가 사라진다.
- 8층이 「적재 압박」인데 가장 쉽다.

노션 `GAMEPLAY CORE` §7 이 정확히 이것을 금지한다 —
「**강한 빌드는 쉬운 승리만 만들지 않고 더 높은 요구량과 사고 위험을 불러야 한다**」.

2026-08-06 자체 검증의 나머지 실패들이 그 원인을 이미 지목하고 있다.

```
적재 정책으로 과적이 도달 가능하다   — 시드 1337 최고 88kg / 허용 130kg
과적이 요구 전력에 배수를 건다       — 무게 98/100 인데 과적이 아님
적재 정책이 칸을 끝까지 채운다       — 시드 555 3/6칸
```

**과적이 사실상 발동하지 않는다.** 대가 축이 배선은 돼 있는데 도달 불가다.

## 6. 아직 헤드리스에서 못 도는 검사

편입을 시도했다가 물렸다. 판정 자체는 순수 로직인데 **파일 단위 의존** 때문에 못 온다.

| 스위트 | 실패 | 막는 것 |
|---|---:|---|
| `Build.Tests.BuildTests` | 5 | `BuildLabelPlacementTests` 를 접어 넣음 → `TubeController`·`TextMeshPro` |
| `Data.Profiles.Tests.ProfileTests` | 2 | `Effects`·`Npc` 경유 → `ParticleSystem`·`Material`·`RunSessionBehaviour` |

대역을 그만큼 넓히면 「흉내 낸 것을 잰다」가 된다(`tools/headless/README.md` 규칙 ②).
넓히지 않았다. 대신 **러너가 매번 그 사실을 출력하게** 했다 —
「헤드리스 93 PASS」를 「전부 통과」로 읽는 것을 출력이 직접 막는다.

**분리 제안 (사용자 결정).** `BuildTests` 에서 `BuildLabelPlacementTests` 접어넣기
한 줄을 빼고 러너 등록으로 옮기면 5건이 헤드리스로 온다. 접어 넣은 이유가
「`Assets/Editor/` 가 그 작업의 소유 경로가 아니었다」는 조직상의 이유였고
(그 파일 주석에 그렇게 적혀 있다) 기술적 이유가 아니다.
