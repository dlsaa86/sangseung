# 부록 C — 성능 프로브가 처음 돌았다. 하나는 실패를 가리킨다

Wave B 배선 직후의 PlayMode 런에서 `RenderBudgetProbe` 와 `MemoryTrendProbe` 가
**처음으로 실제 산출물을 냈다.** 두 항목 다 직전까지 "프로브는 있으나 한 번도 돌리지 않았다"였다.

## C-1. `UP-TECH-08` 메모리 누적 — **요구사항 위반이 측정됐다**

`Logs/memory_trend.txt`. 시드 1337 · 8층까지 · 표본 15개.

```
[층 종료 · 관리 힙]  1.043 GB → 1.080 GB  (+38.40 MB)  상승 7/7  표본당 +5.49 MB
[층 시작 · 관리 힙]  1.043 GB → 1.073 GB  (+30.81 MB)  상승 6/6  표본당 +5.14 MB
[층 종료 · Unity 총] 1.061 GB → 1.069 GB  (+7.90 MB)   상승 7/7  표본당 +1.13 MB
```

**한 번도 내려가지 않고 단조 증가한다.** PRD §17.4 는 "10층 연속 플레이에서 메모리
증가가 지속 누적되지 않음"을 요구한다. 8층까지 +38MB 이므로 10층이면 대략 +50MB 다.

**이 항목을 `VERIFIED` 로 올리지 않는다.** 프로브가 생겼다는 것과 기준을 만족한다는 것은
다르다 — 오히려 지금 처음으로 **만족하지 못한다는 사실이 보이게** 됐다.

주의할 점 두 가지:
- `GC.GetTotalMemory(false)` 는 수집을 강제하지 않으므로 **미수집 쓰레기일 수 있다.**
  다만 `Profiler.GetTotalAllocatedMemoryLong()` 도 함께 단조 증가한다 — 그쪽은
  수집 여부와 무관하므로 "그냥 GC 가 안 돈 것"으로 설명되지 않는다.
- 원인 후보: 스핀마다 `SpinResolution` 의 `Steps`/`Purifies` 배열이 새로 생기고
  `_history` 에 층이 끝날 때까지 쌓인다. 텔레메트리 sink 의 버퍼도 층을 건너 산다.
  **측정 없이 고치지 않는다** — Pass 4 에서 스냅샷으로 어느 쪽인지 가른다.

## C-2. `UP-TECH-07` 렌더링 예산 — 값은 생겼고 판정은 없다

`Logs/render_budget.txt`. 표본 88,310개.

```
[드로우콜]   중앙 218 / 95% 232 / 최악 900
[SetPass]    중앙  63 / 95%  73 / 최악 280
[삼각형]     중앙 17,910 / 95% 23,620 / 최악 34,656
[프레임타임] 중앙 8.45 ms (118 FPS) / 95% 8.72 ms / 최악 147.28 ms
```

프로브가 스스로 "예산이 주입되지 않았다. 값만 기록했고 판정은 하지 않았다"라고 적는다.
`VisualQualityProfile` 의 예산과 대조하는 것이 남은 일이다.

**최악값이 중앙값의 4배**다 (드로우콜 218 → 900, 프레임타임 8.45 → 147ms).
어느 순간인지 아직 모른다 — 캐스케이드일 가능성이 높지만 추측이다.

## C-3. `UP-TECH-04` 의 차단 요인이 **부분적으로** 풀렸다

직전까지 이 항목은 "중앙값 8.33ms 가 vSync 상한이라 90 FPS 를 판정할 수 없다"로 막혀 있었다.
새 프로브는 **`vSync 0 / targetFrameRate -1`** 로 측정하며, 중앙값 8.45ms 는 상한이 아니라
실제 비용이다. 판정 가능한 숫자가 처음 생겼다.

**그러나 아직 완료가 아니다.** 측정 해상도가 **816×714** 로 PRD §13.1 의 1920×1080 이 아니다.
해상도를 올리면 프레임타임이 오르므로 이 118 FPS 를 1080p 성적으로 읽으면 안 된다.
`TargetHardwareProfile` 을 인용해 1080p 로 재측정하는 것이 Pass 4 의 1번 항목이다.

# 부록 D — `CameraRig` 삽입이 1인칭 카메라 높이를 깨뜨렸다 (진단 완료)

## 증상

`WaveBRuntimeProbe` 측정: 카메라 월드 y=3.220, Head 월드 y=1.620.
**카메라가 머리보다 1.6m 높다.** 실내 높이가 2.4m 남짓이므로 시점이 천장 위에 있다.

## 원인 — 소유자가 셋이었다

`FirstPersonController.ApplyEyeHeight()` 가 매 프레임 이렇게 한다:

```csharp
Vector3 localPosition = _viewCamera.transform.localPosition;
localPosition.y = _eyeHeight;      // 1.6
_viewCamera.transform.localPosition = localPosition;
```

**이 코드는 카메라의 부모가 플레이어 루트라고 가정한다.** 그런데 이번에
`CameraRig` 를 `Head`(이미 `EyeHeight = 1.62` 에 있다) 아래에 끼웠으므로
눈높이가 **두 번** 더해진다 — 1.62 + 1.6 = 3.22.

씬에 저장된 카메라 로컬 y=0.98 은 무의미하다. 플레이 시작과 동시에 덮어써진다.

## 왜 아무도 못 잡았나

- **PlayMode 394건 중 카메라 위치를 보는 단정이 하나도 없다.**
- 캡처 하네스는 자기 카메라를 따로 만들어 쓴다(`WaveBProbeCamera`,
  `EyeLevelCapture` 도 좌표를 직접 준다). 그래서 게임 카메라가 어디 있든 그림은 나온다.
- 콘솔 오류도 0이다. 트랜스폼이 이상한 곳에 있는 것은 예외가 아니다.

**한 트랜스폼에 소유자가 셋이었다** — `RiskStateView`(Head 흔들림),
`CollapseSequence`(Rig 낙하), `FirstPersonController`(카메라 눈높이).
둘까지는 알고 분리했고, 셋째를 몰랐다.

## 고치는 방향

`ApplyEyeHeight` 가 **카메라가 아니라 Head 를 대상으로** 하거나,
카메라가 플레이어 루트의 직접 자식이 아닐 때는 강제하지 않는다.
`HumanScaleLayout` 이 이미 Head 를 눈높이에 두므로 후자가 자연스럽다.

## 재발 방지 — 이것이 핵심이다

**PlayMode 에 카메라 눈높이 단정을 넣는다.** 없으면 다음에도 같은 방식으로 깨진다.

    카메라 월드 y 와 Head 월드 y 의 차가 0.05m 이내
    카메라 월드 y 가 칸 천장보다 낮다

`UP-FIX-01`(입구 캡처가 공간의 높이를 못 보여준다)을 포함한 **Pass 3 비주얼 전체가
1인칭 시점 높이에 의존한다.** 천장 위에서 찍은 그림으로 루브릭을 매기면 판정이 무의미하다.

# 부록 E — 세 개의 결함처럼 보인 것이 하나였다: **하네스가 엘리베이터를 싣지 않는다**

오늘 관측값 셋을 처음에 각각 결함으로 읽었다. 전부 원인이 달랐고, **밑바닥은 하나였다.**

| 관측 | 첫 판단 | 실제 |
|---|---|---|
| 같은 좌표에서 보드 4건 불일치 | 결정론 붕괴 | 적재가 달라 규칙이 달랐다 — **정상 동작**이자 `UP-BUILD-02` 의 실런 증거 |
| 캡처가 천장 위에서 찍힌 그림 | 게임 카메라 파손 | 프로브 전용 카메라의 구도. 카메라는 실제로 깨졌지만 **이 그림은 근거가 아니었다** |
| `[승객반응] 시작 0` | 반응 시스템 죽음 | **칸이 비어 있었다.** 승객 0명이면 중재기가 고를 대상이 없다 — 관측 불가이지 고장이 아니다 |

## 밑바닥 원인

**자동 진행 하네스가 화물을 거의 싣지 않는다.**

- 보수 정책: 적재 **0kg** (아무것도 싣지 않는다)
- 공격 정책: 최대 **51kg** / 허용 100kg — 절반에서 멈춘다
- `WaveBRuntimeProbe`: 탑승 절차 자체가 없다

## 이 하나가 막고 있는 것

| 항목 | 왜 막히는가 |
|---|---|
| `UP-BUILD-04` 과적 → 요구 전력·위험 증가 | 과적에 **도달할 수 없다.** EditMode 로만 증명돼 있다 |
| `UP-BUILD-11` 화물 포기 구간 70~89% | 버릴 화물이 없어 소지금 차감 대체 경로만 돈다 |
| `UP-NPC-02·04·05` 승객 반응 | 승객이 없어 **관측 자체가 불가능하다** |
| `UP-SPACE-06` 최대 적재 동선 | 최대 적재 상태가 런에서 발생하지 않는다 |
| 텔레메트리 `overloaded` 필드 | 실전에서 한 번도 true 가 된 적 없다 (문자열 계약 무보호 — 부록 A-2) |

## 그래서 우선순위가 바뀐다

개별 항목을 하나씩 손대는 것보다 **적재하는 정책 하나를 추가하는 것이 다섯 항목의
증거를 한 번에 연다.** 조건:

- 목적지가 먼 무거운 부품을 우선 싣는다 (하차로 빠져나가지 않게)
- 허용 중량을 **넘길 때까지** 싣는다
- 승객을 최소 3명 태운다 (`UP-NPC-05` 의 동시 반응 상한이 걸리려면 3명 이상 필요)

**교훈:** 숫자가 0이면 "안 된다"로 읽기 전에 **"그 상태에 도달했는가"를 먼저 묻는다.**
오늘 세 번 중 두 번은 도달하지 않은 것이었다.

# 부록 F — Wave B 가 남긴 운영 주의사항과 내 코드의 결함 2건

## F-1. **빌더 실행 순서를 지키지 않으면 Wave B 배선이 사라진다**

`GrayboxWorldBuilder.Build()` 는 `GrayboxWorld` 루트를 **통째로 파괴하고 다시 만든다.**
그 아래에 이번에 만든 `AccidentPrinter` 와 `CeilingLampRig` 가 있다.

**올바른 순서:**

    Build Graybox World  →  Layout  →  Ascend/Wire Pass 1 Wave B

순서를 어기면 프린터와 천장등 리그가 사라지고 **콘솔에는 아무것도 남지 않는다.**
`Pass1WaveBWiring` 은 멱등이므로 마지막에 한 번 더 돌리면 복구된다 —
**모르고 지나가는 것이 문제이지 복구가 어려운 것이 아니다.**

## F-2. 리그가 **둘** 필요했다 — 내 브리핑은 하나만 지목했다

`RiskStateView` 가 매 LateUpdate 마다 절대값으로 덮어쓰는 트랜스폼은 둘이다.
`_cameraTarget`(=`Head`)뿐 아니라 **`_swayTarget`(=`CeilingLamp`)** 도 그렇다.
그래서 `CeilingLampRig` 도 끼워야 했다. 내가 브리핑에 카메라만 적었고
씬 오너가 나머지를 찾아냈다.

**같은 부류를 한 번 더 놓쳤다는 뜻이다** — 부록 D 의 세 번째 소유자(`FirstPersonController`)와
합치면, 이 씬에서 "누가 이 트랜스폼을 쓰는가"를 전수로 세어 본 적이 없다.
Pass 2 에서 `LateUpdate` 에 `localPosition` 을 쓰는 모든 컴포넌트 목록을 한 번 만든다.

## F-3. 내 코드 결함 — `_gazeCeiling` 을 배선하면 **오히려 위를 안 본다**

`BuildFigureView.GazeRotation` 은 모든 시선에서 `delta.y = 0` 으로 눌러 수평 성분만 쓴다.
`Ceiling` 만 **대상이 null 일 때** `-28°` 폴백이 걸리게 돼 있다.
따라서 천장 트랜스폼을 꽂으면 폴백이 사라지고 수평을 보게 된다 — 의도와 정반대다.

씬 오너가 코드를 읽고 **일부러 비워 뒀다.** 옳은 판단이지만
"배선하면 깨지는 필드"를 인스펙터에 노출해 둔 것은 내 설계 결함이다.
`Ceiling` 은 평탄화에서 제외하도록 고친다.

## F-4. 내 코드 결함 — 종이 테이프 글자가 테이프를 넘친다

`PaperTapePrinterView.EnsureParts` 의 상수 조합이 서로 맞지 않는다.
테이프 폭 0.28m · 줄 높이 0.035m · `fontSize 0.9` 인데 **한글은 전각**이라
22자 헤더가 약 0.52m 를 요구하고 실제로 1.16m 가 렌더된다.

**폰트만 줄이면 줄 높이가 어긋나고 테이프를 넓히면 장치 크기가 바뀐다.**
숫자 하나로 끝나지 않으므로 씬 오너가 추측하지 않고 남긴 것이 옳다.
테이프 폭·줄 높이·폰트 크기를 **한 벌로** 다시 잡는다 (Pass 3).
