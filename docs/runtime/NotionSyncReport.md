## 3.2 패턴 배수·캐스케이드 배수 — 전부 신규

근거: **08 기술부록 §8.3, §8.4, §8.5, §9.2**

패턴 배수:
- 개수 정화 **×1.0**
- 직선 3개 **×1.5**
- 4개 연결 **×2.0**
- 5개 연결 **×2.5**
- 6개 이상 연결 **×3.0**

패턴 우선순위(동일 저항체에 중복 판정 시): `6개 이상 연결 → 5개 연결 → 4개 연결 → 직선 → 개수 정화`

캐스케이드 단계 배수:
- 1단계 ×1.0 / 2단계 ×1.25 / 3단계 ×1.5 / 4단계 ×2.0 / **5단계 이상은 단계당 +0.5**
- **캐스케이드 배수는 해당 단계에서 발생한 정화 전력에만 적용한다.** (누적 전체에 적용하지 않는다)

가중치 계산 순서 7단계 (§7.2): `심볼 기본 가중치 → 계약 보정 → 증식체 잔류 보정 → 승객 효과 → 부품 효과 → 층 규칙 보정 → 최종 최소값 보정`
- 최종 가중치는 음수가 될 수 없다.
- **모든 심볼의 합산 가중치가 0이면 스핀을 중단하고 명시적 오류를 출력한다.**

저장소 `TECH_SPEC.md` §8은 순서만 있고 배수·경계 규칙이 없다.

## 3.3 계약 보정 수치 — 전부 신규

근거: **08 기술부록 §10.2, §10.3, §10.4**

| 계약 | 등장 가중치 | 정화 전력 | 잔류 대가 |
|---|---|---|---|
| 흡수체 계약 | **×1.6** | **×1.5** | **×1.5** |
| 증식체 계약 | **×1.6** | **×1.35** | **×1.5** |

## 3.8 영혼 구슬·저항체 시각 디자인 사양 — 신규 (사용자 지정 확인 항목)

### 공통 형태 규칙
- 모든 심볼은 **통관 안에서 안정적으로 순환할 수 있는 유사한 구형 부피**를 가진다.
- **외곽 실루엣과 내부 코어를 종류마다 명확히 다르게** 만든다.
- **작은 글자와 복잡한 표면 장식은 사용하지 않는다.**
- 정면뿐 아니라 **회전 중에도 인식되도록 문양을 여러 면에 반복하거나 내부 코어 자체를 차별화**한다.

- 정상 영혼은 "완전히 선하고 깨끗한 인상"보다 **이미 정제·순응된 존재**처럼 보이게 한다.
- 저항체는 "단순한 악성 바이러스"보다 **내부에서 무언가가 버티거나 움직이는 인상**을 준다.

### 정상 영혼 (`normal_soul`)
- 둥글고 **안정된 외곽**
- **일정한 방향의 느린 회전**
- 부드럽고 **반복적인 내부 맥동**
- 표면 문양이 정돈되어 있으며 **돌출이 적음**
- 판정 시 **전력 탱크 방향으로 흡수되는 명확한 이동**

### 흡수체 (`absorber`)
- **중앙이 비어 있거나 안쪽으로 빨려 들어가는 코어**
- **표면에서 중심으로 향하는 홈**
- **전력 탱크 방향으로 가는 가느다란 흡수 실선**
- **낮고 지속적인 진동**
- 정화 연출 3종: 기본 정화 = 중심 공백이 닫히며 붕괴 / 직선 = **세 심볼을 관통하는 절단선** / 연결 붕괴 = 연결된 코어가 한꺼번에 압착되고 빈칸으로 빨려 나감

### 증식체 (`replicator`)
- **하나의 구체 안에 작은 핵이 여러 개** 존재
- 표면에 **분열선과 새싹처럼 돋는 돌기**
- 판정 종료 직전 **작은 핵이 복제될 듯 팽창**
- **고음의 반복 클릭 또는 맥동**
- 정화 연출 3종: 기본 정화 = 내부 핵이 동시에 터짐 / 직선 = **분열선이 직선으로 이어져 연쇄 폭발** / 연결 붕괴 = 작은 핵이 주변 칸으로 퍼지려다 **역으로 빨려 들어감**

### 저항 계약 시각 표시
- 계약한 저항체에는 **장치 외곽의 전용 표식과 동일한 링**을 표시한다.
- **계약 심볼 등장 시 과도한 희귀 연출을 사용하지 않는다** — 많이 나와야 하는 대상이므로 일관된 강조만 사용.
- 계약한 저항의 패턴이 성립하면 **전용 계약 계기판이 충전**된다.

### 패턴 시각화 규칙
- **개수 기본 정화**: 3개 이상에 같은 외곽 윤곽선, 위치가 떨어져 있어도 **번호·색상·맥동을 통일**, 보상 표시는 작고 빠르게
- **직선 3개**: 관통하는 한 줄의 강한 효과, **직선 방향에 따라 장치 내부 기계 부품이 반응**, 기본 정화보다 큰 충격과 배수 표시
- **4개 이상 연결**: 연결 칸을 **하나의 면처럼** 채움 → **외곽선이 먼저 닫힌 뒤 내부가 붕괴** → 제거된 칸의 빈 공간을 명확히 보여준 뒤 새 심볼 충전

- **흡수체 붕괴 파츠**

## 3.11 위험 상태 4단계 세부 연출 사양 — 신규

근거: **MASTER PRD Notion §8.2, §8.3, §8.4**

저장소 `VISUAL_SPEC.md` §6과 `MASTER_PRD.md` §9는 단계 이름과 방향성만 기술한다. Notion은 채널별 구체 사양을 가진다.

- **Stable**: 따뜻하고 희미한 기본 조명 / 일정한 모터음과 미세한 정상 진동 / **계기판 바늘 안정** / 승객의 중립 대기 모션
- **Strain**(저장소 명칭 Warning): **천장등이 짧게 어두워짐** / 간헐적인 낮은 `쿵`과 바닥 진동 / **계기판 바늘 미세 진동** / **천장 먼지와 녹가루** / **승객 한 명이 위 또는 벽을 바라봄**
- **Critical**: 일반 조명 일부 소등 + **회전식 붉은 비상등 활성** / 일정한 사이렌보다 **저주파 `쿠웅`의 반복 간격이 짧아짐** / 문과 철판 미세 떨림 / **화물과 매달린 부품이 흔들림** / **짧은 수직 낙하 충격** / 승객이 벽·난간을 붙잡고 플레이어를 바라봄
- **Collapse**: 사이렌과 모터가 **갑자기 끊김** / **0.3~0.7초 암전과 정적** / 거대한 금속 파열음 / 급강하 또는 강한 제동 충격 / **붉은 비상등이 불규칙하게 재점등** / 화물·승객의 물리적 반응

- 카메라 셰이크 강도·사이렌 음량·섬광 강도는 **접근성 옵션으로 분리**한다.

### 왜 위험한가

**(a) Notion 쪽 — 프롬프트를 실행하면 폐기된 장치가 만들어진다**

Notion 06 §13은 **같은 절 안에서 자기모순**한다. 「필수 파츠」는 "통관별 정지 버튼 없음"이라고

```
one large mechanical stop button directly below each corresponding pipe,
one shared heavy purge lever positioned clearly below the three buttons,
hostile resistance spheres can be stopped and aligned at the three capture windows,
clear mechanical relationship between each pipe, its capture window and its button,
```

같은 절의 「시각 우선순위」도 "**통관 3개와 버튼 3개의 대응 관계**", "배출 레버의 강한 물리적
조작감", "**파쇄** 시 균열 단계"를 남기고 있고, 「저항체와 정상 영혼 이미지 규칙」은
"**파쇄용 저항체는 온전함·미세 균열·심한 균열·파열 직전의 최소 4상태**"와
"**정상 영혼 오배출 VFX**"를 요구한다. '오배출'은 Notion 99번 「프로토타입에서 제외할 것」에
**"정상 영혼 오배출 판정"으로 명시 폐기**된 개념이다.

> **이 프롬프트를 그대로 이미지 생성에 넣으면 정지 버튼 3개가 달린 폐기된 장치 에셋 세트가
> 만들어진다.** 생성 1회로 통관·버튼·레버·결과창 전체가 잘못된 구조로 고정되고,
> 그 위에서 모델링·텍스처링이 진행되면 되돌리는 비용이 급격히 커진다.
> **3D 리소스 제작 착수 전에 반드시 교정해야 한다.**

**(b) 저장소 쪽 — 폐기 구조가 씬에 이미 존재한다** *(본 감사에서 신규 발견)*

- 씬에 **`StopButton_1/2/3`, `ButtonPivot_1/2/3`, `ButtonLabel_1/2/3`이 실재한다.**

> 별도 패스가 숨겨야 한다. **숨김 패스가 한 번이라도 누락되면 폐기된 조작부가 화면에 노출되고,

# 8. 감사 방법과 한계

**방법**
1. `ToolSearch`로 Notion MCP 도구(`notion-fetch`, `notion-search`, `notion-query-data-sources`) 스키마 로드
2. 지시받은 MASTER PRD·기술 부록 2개 페이지 `notion-fetch`
3. MASTER PRD §20 「관련 원본」의 10개 링크와 루트 페이지 인덱스를 따라 하위 페이지 전수 조회
4. 99번 하위 페이지(3D 리소스 타겟), 아카이브 페이지까지 추적
5. 개발 티켓 DB는 `notion-query-data-sources` SQL로 10행 전량 조회
6. 저장소 5개 문서 전문 읽기 + 승객 에셋·`docs/` 디렉터리 실측 대조

**한계**
- `notion-search`는 사용하지 않았다. **링크 추적만으로 워크스페이스 루트 하위 전체(13개 엔터티)에 도달했고 접근 실패가 0건**이었기 때문이다. 루트 트리 **밖**에 별도 관련 페이지가 존재할 가능성은 배제하지 못한다.
- 페이지 스냅샷 시각은 대부분 **2026-07-30T02:2x~02:3x**다. 그 이후 Notion 편집이 있었다면 반영되지 않는다.
- 코드 대조는 승객 정의 에셋과 데이터 디렉터리 구조에 한정했다. **룰렛 판정 로직의 실제 수치가 §3.1~3.3과 일치하는지는 검증하지 않았다** — 본 감사는 문서 대 문서 동기화가 범위다.
- 🔴 **저장소가 감사 도중 변경됐다.** 다른 에이전트(`agent/phase2-full-prototype`)가 동시에 작업하며 `CURRENT_PHASE.md`(194줄), `DECISION_LOG.md`(+57줄, D-20260731-01~03), `ASSUMPTION_LOG.md`, `README.md`, `Scripts/Run/*.cs`, `Scripts/Spin/FloorPlan.cs`를 수정하고 `Scripts/Build/`, `tools/`를 추가했다. **§2 매핑표는 승격 이전 `CURRENT_PHASE.md` 기준이므로 해당 문서 대조는 재확인이 필요하다.** `MASTER_PRD.md`·`TECH_SPEC.md`·`VISUAL_SPEC.md`는 감사 기간 중 변경되지 않아 매핑이 유효하다.
- 저장소 파일은 **하나도 수정하지 않았다.** 생성한 파일은 이 보고서 1개뿐이다. 위 변경은 전부 다른 에이전트의 작업이다.
