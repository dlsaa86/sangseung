# 헤드리스 밸런스 감사 — 표본을 100배로 키우면 무엇이 달라지는가

> 실행일: 2026-08-05 · 도구: `tools/headless/` · 유니티 미사용
> 대상: `Assets/Editor/BalanceSweep.cs` · `Assets/Editor/CurriculumCoverageProbe.cs`
> **이 문서는 손으로 썼다.** 아래 인용된 수치는 전부 `tools/headless/` 산출이고
> 재현 명령을 각 절에 적었다.

---

## 0. 무엇을 했나 — 판정 코드를 에디터 밖으로 꺼냈다

`BalanceSweep` 은 `UnityEditor` 를 **`[MenuItem]` 어트리뷰트로만** 쓰고, 그것이 부르는
판정 계층(`Spin` · `Run` · `Build` · `Risk` · `Data.Profiles`)은 전부 순수 C# 이다.
그래서 `UnityEngine` · `UnityEditor` 의 **최소 대역**만 만들어 주면 같은 소스가
.NET 8 에서 그대로 컴파일된다. 실제로 **툴 코드는 한 줄도 고치지 않았다** —
표본 수를 여는 것 외에는(§6).

포팅이 아니라 대역인 것이 중요하다. 툴을 베껴 고치는 순간 두 갈래가 되고,
이 저장소가 반복해서 당한 실패가 정확히 그것이다 — **재는 도구가 다른 게임을 잰다.**

### 대역이 결과를 바꾸지 않았다는 증거

헤드리스 산출을 유니티가 만든 `docs/runtime/BALANCE_REPORT.md`(2026-08-04 06:32)와
같은 표본(시드 20000~20299)으로 대조했다.

| | 결과 |
|---|---|
| 전체 diff | 27줄 |
| 그중 **숫자가 다른 줄** | **0줄** |
| 다른 줄의 정체 | 전부 산문 — 소스가 보고서보다 최신이라 §2·§3 해설 문단이 갱신돼 있다 |

표에서 유일하게 갈린 행조차 목표 열의 라벨이고 실측값은 `0.663` 으로 동일하다.
**대역은 숫자에 손대지 않는다.**

### 속도

| | 유니티 에디터 | 헤드리스 |
|---|---|---|
| 시드 300 × 정책 3종 | 도메인 리로드만으로 수십 초 | **1.0초** |
| 시드 30000 × 정책 3종 | (돌린 적 없음) | **33초** |
| 커버리지 시드 20000 × 정책 3종 | (돌린 적 없음) | 11초 |

속도가 만드는 것은 편의가 아니라 **분해능**이다. 아래가 그 이야기다.

재현:
```bash
cd tools/headless && dotnet run -c Release -- sweep 30000
```

## 1. 가장 중요한 결과 — 통과하던 지표 하나가 실제로는 미달이다

`FUN_CRITERIA` §4 「3연쇄 이상 스핀 비율」의 목표는 `5–15%` 다.

| 표본 | 실측 | 판정 |
|---|---|---|
| 시드 300 (현재 커밋된 보고서) | 14.7% | ✅ |
| **시드 30000** | **15.1%** | **❌** |

넘긴 폭은 0.1%p 라 「거의 같다」로 읽고 싶어지지만, **그게 정확히 문제다.**
서로 겹치지 않는 300 시드 블록 24개로 같은 스윕을 돌리면 이 지표는
**14.5% ~ 15.8%** 사이를 오간다(§2 표). 즉 시드 300 에서 이 항목의 ✅/❌ 는
**어느 시드 블록을 뽑았는가로 결정된다.** 커밋된 보고서의 ✅ 는 판정이 아니라
동전 던지기였다.

같은 30000 시드에서 **다른 모든 지표는 대역 안**이다. 미달은 이 하나뿐이다.

> **이 수치를 어떻게 고칠지는 여기서 정하지 않는다.** 캐스케이드 빈도는
> 판 구성·정화 규칙·잔류 가중치가 함께 만드는 값이라, 한 다이얼을 돌리면
> §4 「정화 발생 스핀 비율」(현재 59.7%, 목표 35–65%)이 같이 움직인다.
> 두 지표를 한 번에 보는 탐색이 필요하고, 그건 이 감사의 범위가 아니다.

## 2. 시드 300 은 대역 판정에 필요한 분해능이 없다

겹치지 않는 300 시드 블록 24개(총 7200 시드)로 각 지표가 **표본 잡음만으로**
얼마나 흔들리는지 쟀다. 게임은 하나도 바뀌지 않았고 시드만 다르다.

| 지표 | 목표 대역 | 대역 폭 | 잡음 폭(최소~최대) | 판정 가능? |
|---|---|---:|---|---|
| 초반 1–3 클리어율 | 97–100% | 3.0%p | 97.8 ~ 98.9 (1.1%p) | ✅ 가능 |
| 중반 4–7 클리어율 | 90–96% | 6.0%p | 93.1 ~ 95.2 (2.1%p) | ✅ 가능 |
| **후반 8–10 클리어율** | 82–92% | 10.0%p | **86.1 ~ 91.5 (5.4%p)** | ⚠ 대역의 절반 |
| 선택 발생 층 비율 | 40–85% | 45.0%p | 77.2 ~ 79.5 (2.3%p) | ✅ 가능 |
| 과수확 선택률 | 25–75% | 50.0%p | 45.2 ~ 55.8 (10.6%p) | ✅ 가능 |
| **3연쇄 이상 비율** | 5–15% | 10.0%p | **14.5 ~ 15.8 (1.3%p)** | ❌ **경계 위** |
| 정화 발생 비율 | 35–65% | 30.0%p | 58.6 ~ 60.7 (2.1%p) | ✅ 가능 |
| **10층 방문률** | (커리큘럼 근거) | — | **54.3 ~ 64.0 (9.7%p)** | ❌ |
| **EV 비율** | (판정 안 함) | — | **0.51 ~ 5.13 (σ=0.92)** | ❌ 통계 아님 |
| 관측 최대 연쇄 | (참고) | — | 10 ~ 17 (30000에서는 **20**) | ❌ 표본 종속 |

읽는 법 셋.

**① 대역이 넓은 지표는 300 으로 충분하다.** 「과수확 선택률 25–75%」처럼 폭이 넓으면
잡음 10.6%p 가 판정을 뒤집지 못한다. 이 항목들은 표본을 키울 이유가 없다.

**② 대역이 잡음보다 좁거나 비슷하면 그 판정은 정보가 아니다.** 후반 클리어율은
대역 10%p 에 잡음 5.4%p 다 — 「대역 안」이라는 말은 맞지만 **대역 어디쯤인지는
못 말한다.** 30000 시드의 참값은 **89.2%** 로 상단(92%)에서 2.8%p 거리다.
커밋된 보고서의 86.1% 를 보고 「중간쯤」이라고 읽었다면 그건 잡음의 아래 꼬리였다.

**③ 최대값·비율의 비율은 표본 크기의 함수라 애초에 비교 불가다.**
「관측 최대 연쇄」는 표본이 커지면 반드시 커진다 — 300 에서 13, 30000 에서 **20**,
즉 **하드 캡에 정확히 닿았다**(`UP-CORE-09` 캐스케이드 캡 20). 300 시드만 보던
동안에는 「캡은 이론적 안전장치」였지만, 실제로 **닿는다.** 안전 종료 경로가
장식이 아니라 실행 경로라는 뜻이다.
`EV 비율`은 분모가 0 근처로 갈 수 있어 σ 가 평균과 맞먹는다 — 이미 「판정 안 함」으로
강등돼 있지만, **값을 보고서에 인쇄하는 것 자체가 오해를 만든다.**

재현:
```bash
cd tools/headless && dotnet run -c Release -- replicate 300 out/replicate.md 24
```

## 3. 적재는 선택이 아니다 — 「무엇을 실을까」는 선택이고 「얼마나 실을까」는 아니다

`CurriculumCoverageProbe` 의 적재 축을 0~6개로 늘려 시드 8000 개씩 돌렸다.

| 층당 적재 | 완주율 | 10층 도달률 |
|---:|---:|---:|
| 0개 | 23.8% | 27.6% |
| 1개 | 32.5% | 35.8% |
| 2개 | 41.5% | 44.4% |
| 3개 | **46.0%** | **48.5%** |
| 4개 | 46.0% | 48.5% |
| 5개 | 46.0% | 48.5% |
| 6개 | 46.0% | 48.5% |

### ① 곡선이 꺾이지 않는다

적재는 무게 → 요구 전력·과적 위험으로 **대가를 치르게** 설계돼 있다. 그런데 완주율은
적재량에 대해 **단조 증가**하고 어디서도 내려오지 않는다. 즉 현재 수치에서
**「전부 싣는다」가 지배 전략**이다.

대가가 아예 없는 것은 아니다 — 매 층 최대 적재로 시드 4000 개를 돌린 별도 실측:

- 과적을 한 번이라도 겪은 런 **21.70%** (868/4000)
- 과적이 발생한 층 **5.47%** (1703/31160)
- 무게/허용치 비율 평균 0.500 · **최대 1.260**

**과적은 실제로 발생한다.** 다만 그 대가가 적재 이득을 **한 번도 넘지 못한다.**
「위험이 작동하지 않는다」가 아니라 **「위험이 결정을 만들 만큼 크지 않다」**가
정확한 진술이다. 둘은 다른 처방을 부른다.

### ② 3개에서 포화하는 이유는 무게가 아니라 **제안 개수**다

4·5·6개의 수치가 3개와 **비트 단위로 동일**하다. 원인은 `FloorSession.BuildOfferCount = 3`
— 층당 제안이 3개뿐이라 4개째부터 실을 것이 없다. 실측 「층당 실제로 실린 개수」는
평균 **2.86 · 최대 3**.

즉 **적재 상한을 정하는 것은 허용 중량이 아니라 제안 개수다.** 무게 시스템은
상한에 닿기 전에 끝난다. `UP-SPACE-06`(최대 적재 상태에서도 동선 유지)이 말하는
「최대 적재」는 지금 **무게 100 의 한계가 아니라 제안 3개의 한계**를 뜻한다.

### ③ 시드 200 은 이 결론을 낼 수 없었다

| 층당 적재 | 시드 200 | 시드 20000 |
|---:|---:|---:|
| 0개 | 27.0% | **22.7%** |
| 1개 | 28.5% | **32.0%** |
| 2개 | 39.5% | **40.8%** |

시드 200 에서 0개와 1개는 27.0% 대 28.5% 로 붙어 있어 「1개는 의미 없다」로 읽힌다.
그 1.5%p 는 잡음이었고, 참값은 **9.3%p 차이**다. 적재 축의 모양 자체가 달랐다.

재현:
```bash
cd tools/headless && dotnet run -c Release -- loadcurve 8000
cd tools/headless && dotnet run -c Release -- overload 4000
```

## 4. 시드 300 이 맞았던 것 — 뒤집지 않아도 되는 판정

표본을 100배로 키워도 **결론이 바뀌지 않은** 항목을 함께 적는다. 감사가 흔들린
것만 적으면 「전부 못 믿는다」로 읽히는데, 그건 사실이 아니다.

| 항목 | 시드 300 | 시드 30000 | 결론 |
|---|---|---|---|
| 초반 1–3 클리어율 | 98.8% ✅ | 98.3% ✅ | 유지 |
| 중반 4–7 클리어율 | 94.4% ✅ | 94.3% ✅ | 유지 |
| 선택이 발생하는 층 비율 | 78.0% ✅ | 78.4% ✅ | 유지 |
| 과수확 선택률 | 51.0% ✅ | 49.4% ✅ | 유지 |
| 정화 발생 스핀 비율 | 58.6% ✅ | 59.7% ✅ | 유지 |
| 4층 「너무 쉽다」 경고 | ⚠ 1.30 스핀 | ⚠ 1.34 스핀 | 유지 |

특히 **4층 경고는 표본과 무관하게 계속 뜬다.** 요구 전력 630 에 이론 소요 스핀 1.34 —
`BalanceSweep` 주석이 「4층만 약한 쪽(무계약)에 맞춘다」고 의도를 적어 둔 그 층이다.
의도된 값이므로 결함이 아니지만, **경고가 계속 뜨는 한 그 의도는 매 보고서마다
다시 설명돼야 한다.** 경고 문구에 예외 사유를 넣는 편이 낫다.

## 5. 이 감사가 답하지 못하는 것

- **재미·긴장·손맛.** 봇은 감정을 만들지 않는다. `BALANCE_REPORT` §7 과 같은 한계다.
- **연출 계층 전부.** 대역은 `MonoBehaviour` 를 컴파일하지만 실행하지 않는다.
  `RiskStateView` · `SpinPresenter` · 오디오는 이 하네스에서 한 프레임도 돌지 않는다.
- **적재의 공간적 대가.** 「최대 적재 상태에서도 장치에 손이 닿는가」(`UP-SPACE-06`)는
  무게 숫자가 아니라 씬 배치의 문제다. §3 의 결론은 **수치 축에 한정된다.**
- **계약 선택.** `CurriculumCoverageProbe` 는 계약을 항상 0번으로 고정한다.
  §3 의 적재 곡선은 「계약을 안 고르는 플레이어」의 곡선이다.
- **인간의 조작 정확도.** 세 정책 전부 완벽한 정보와 무한한 인내를 가정한다.

## 6. 프로젝트에 들어간 변경

기존 판정 로직은 **하나도 건드리지 않았다.** 표본 수를 상수에서 정적 필드로 연 것과
적재 축을 배열로 연 것 둘뿐이고, **기본값은 예전과 같다.**

| 파일 | 변경 | 기본 동작 |
|---|---|---|
| `Assets/Editor/BalanceSweep.cs` | `SeedCount`·`FirstSeed`·`CalibrationSeeds` 를 `const` → `public static` (+ `ResetSampling()`) | 300 / 20000 / 120 — **동일** |
| `Assets/Editor/CurriculumCoverageProbe.cs` | 같은 셋 + 적재 축 `LoadCounts` 신설 | 200 / 1000 / `{0,1,2}` — **동일** |
| `tools/headless/` | 신규. 대역 + 러너 + 프로브 2종 | — |

기본값 동일성은 실측으로 확인했다 — 축을 열기 전후의 `coverage` 산출이
**byte 단위로 같다.** `sweep` 도 시드 300 에서 같다.

> ⚠ **표본을 키운 채로 두지 않는다.** 보고서 머리글에 시드 범위가 찍히므로
> 서로 다른 표본 수의 보고서를 비교할 때는 **그 줄을 먼저 읽는다.**
> 러너는 끝날 때 `ResetSampling()` 을 부른다.

## 7. 다음에 할 것 (우선순위)

1. **3연쇄 이상 비율 15.1%** 를 대역 안으로 되돌린다. 단, §4 정화 비율(59.7%)이
   같이 움직이므로 **두 지표를 함께 보는 탐색**이 필요하다. 헤드리스에서 한 번에
   33초이므로 격자 탐색이 실용적이다.
2. **적재를 결정으로 만든다.** 지금은 「전부 싣는다」가 항상 최선이다. 방향 셋 —
   ① 과적 페널티를 키운다 ② 제안 3개에 **서로 배타적인 성격**을 준다(무게가 아니라
   빌드 방향이 갈리게) ③ 무게 외의 대가(공간·시야·이동 속도)를 건다.
   **②가 PRD §2.3 의 「명확히 다른 두 빌드 전략」에 가장 가깝다.**
3. **`FUN_CRITERIA` 에 표본 수 요구를 적는다.** 지표마다 필요한 최소 시드가 다르다 —
   §2 표가 그 근거다. 대역이 좁은 지표에 300 시드 보고서를 인용하지 않는다.
4. **`EV 비율` 을 보고서에서 뺀다.** 이미 판정하지 않는데 인쇄되고 있고,
   시드 300 에서 σ 가 평균과 맞먹어 **값 자체가 오해를 만든다.**
