## 1. 셀 실측 — 오브젝트, 방법, 구슬 지름 결정

### 1.1 무엇을 쟀나

`SOCKET_ElevPanel` 자식 중 `SM_Chamber_Glass_01~09` 9개가 3×3 현창(포탈글라스) 배열이다
(`AscendAD47Board.cs`의 `BuildNormal` 등이 셀 앵커로 쓰는 바로 그 오브젝트 — 코드에
"앵커가 챔버 유리로 바뀌었다"는 주석이 있어 확인했다). `SM_Chamber_Glass_01` 하나를
정밀 측정했다 (9개 전부 같은 치수로 조립되어 있어 대표 1개면 충분).

| 항목 | 값 |
|---|---|
| 월드 X 폭 | 0.23204 m |
| 월드 Z 높이 | 0.23204 m (X와 동일 — 원형 확인) |
| 반지름 방향 거리 (중심→정점, XZ 평면) | min 0.00000 (중심 정점) ~ max 0.11602 |
| 정점 수 | 113 |

X 폭과 Z 높이가 정확히 같고 반경 실측(0.11602×2=0.23204)이 bbox 폭과 일치 — 원형
디스크가 맞다. **이것을 "한 칸의 실제 안지름"으로 채택했다.**

### 1.2 구슬 지름

```
셀 안지름       0.23204 m  (실측, 추정 아님)
채택 비율       65%  (지시 범위 60~70%의 중간값)
구슬 지름       0.150826 m  (150.83mm)
구슬 반지름     0.075413 m  (75.41mm)
```

### 1.3 `ReferenceRoomSpec.cs` 기존 상수와의 불일치 — 기록만 하고 따르지 않음

코드에 이미 이 계기용 상수가 있다.

```csharp
WindowGlassDiameter = 0.29f;              // "약 0.25~0.29m" 지시, 상한
SoulRadius = WindowGlassDiameter * 0.20f; // = 0.058  (지름 0.116, 유리 지름의 40%)
```

두 가지가 실측과 어긋난다.

1. **`WindowGlassDiameter`(0.29) 자체가 실제 메시(0.232)보다 25% 크다.** 이 블렌더
   파일의 챔버 유리는 스펙 문서보다 작게 지어져 있다 — Phase 1에서 겪은 것과 같은
   종류의 문서-실물 드리프트다.
2. **`SoulRadius` 비율(유리 지름의 40%)을 그대로 썼다면 구슬 지름은 92.8mm**였을 것이다
   (실측 232mm × 0.40). 이번 지시(60~70%)를 적용한 150.8mm는 그보다 **63% 더 크다.**

이 상수를 "틀렸다"고 고치지 않았다 — 지시가 명시적으로 새 비율(60~70%)을 줬고,
챔버 안에 최종 배치하는 것은 team-lead 몫이다("Unity 반영 위치는 내가 정한다").
대신 아래를 반드시 알아야 한다.

> `SoulRadius` 주석: "⚠ 첫 값 0.30(반지름 비율)은 챔버 후면을 뚫었다 — 뒷면 반경
> 0.1118 > 여유 0.0980." 즉 **이 챔버는 과거에 한 번 "너무 큰 구슬"로 실제 파손을
> 겪었다.** 지금 채택한 150.8mm 지름(반지름 75.4mm)이 실측 유리 지름(232mm) 기준
> 32.5% 비율인데, 과거 사고를 냈던 비율(유리 지름 290mm 기준 30%)과 절대적 크기가
> 비슷한 영역이다. **챔버 안에 실제로 넣을 때 후면 클리어런스를 반드시 재확인해야
> 한다** — 이번 세션은 3개를 캐빈에서 5m 떨어진 빈 공간에 뒀을 뿐 챔버 안에 넣지
> 않았으므로 이 검증을 하지 못했다.

## 2. 3종 형태 설계

셋 다 `SOCKET_ElevPanel`의 자식이 **아니다** (부모 없음, top-level) — 최종 배치·부모는
team-lead가 정하므로 부모의 1.37724배 스케일에 얽히지 않게 독립 오브젝트로 뒀다.
로컬 좌표 = 월드 좌표.

**정면 축 규약**: 이번 세션 전체에서 **-Y 를 "정면"(카메라 쪽)으로 정의했다.**
검증 카메라는 Y=-3 에서 +Y 방향을 보고, 각 오브젝트의 특징(흡수체 입, 증식체 혹
배치)은 -Y 쪽으로 쏠려 있다. Unity에서 배치할 때 이 축 관례를 참고해야 한다 —
챔버의 실제 "플레이어 쪽" 축과 다를 수 있으니 대조 후 필요하면 오브젝트를 통째로
회전시키면 된다 (형상 자체를 다시 만들 필요는 없다).

### 2.1 `SM_Sym_NormalSoul` — 정상 영혼

| 항목 | 값 |
|---|---|
| 형태 | 저해상도 UV 스피어, 돌출부 0, 단일 실루엣 |
| 세그먼트 | u=10, v=7 |
| 정점 / 삼각형 | 62 / **120** (셋 중 가장 낮음 — 지시 "정상 영혼은 더 낮게" 충족) |
| 바운딩 박스 (m) | X 0.13985 · Y 0.14704 · Z 0.15083 |
| 재질 | `M_Cab_Bulb` |

가장 단순한 실루엣이어야 한다는 요구를 그대로 따랐다 — 어떤 조작도 하지 않은
순수 구체다. 나머지 둘은 이것의 "변형"으로 읽혀야 한다.

### 2.2 `SM_Sym_Absorber` — 흡수체

| 항목 | 값 |
|---|---|
| 형태 | 구체 한쪽을 **평면으로 절단**해 만든 오목한 입 (아래 §4 참조 — 최종 기법) |
| 세그먼트 | u=12, v=8 |
| 정점 / 삼각형 | 86 / **168** |
| 바운딩 박스 (m) | X 0.12974 · Y 0.15083 · Z 0.15083 |
| 재질 | `M_Elev_CavityDark` |
| 절단 축 | `(-1.0, -0.1, 0.05)` 정규화 — 거의 순수 -X (실루엣 경계 쪽), Y 성분은 살짝만 둬서 입 안쪽 면이 정면에서 아주 조금 보이게 함 |
| 절단 깊이 | 반지름의 65% 지점에서 편평화 (구면 반경으로 스케일하지 않고, 그 지점 너머 모든 정점을 축에 수직한 평면 위로 투영) |

**왜 "평면 절단"인가 — §4의 실패 3회를 만든 원인과 그 수정.** 처음 세 번의 시도는
전부 정점을 중심 쪽으로 **부드럽게 반경 축소**하는 방식이었다(구 표면을 유지한 채
반경만 각도에 따라 줄임). 이 방식은 오목함이 **음영으로만** 읽힌다 — 순수 단색
실루엣(재질 없음, 음영 없음)에서는 윤곽선이 완만한 곡선으로 남아 정상 영혼과
거의 구분되지 않았다. 4~5번째 시도에서 방식을 바꿔, 절단면 너머의 정점을 **평면
위로 강제 투영**했다 — 이러면 원의 곡선 일부가 **직선(현)으로 대체**되어 순수
윤곽선 비교에서도 확실히 다르게 나온다. 실측 대조는 §4.

### 2.3 `SM_Sym_Proliferator` — 증식체

## 6. 재질 선택 근거

색은 보조 수단이라고 못박혀 있어 셋의 **형태**가 이미 갈리는 것을 확인한 뒤에
골랐다. 새 머티리얼은 만들지 않았고, 후보 9개의 실제 셰이더 값(블렌드 모드·알파·
발광)을 전부 조회해서 골랐다 — 이름만 보고 고르지 않았다.

| 심볼 | 재질 | 선택 이유 | 기각한 후보 |
|---|---|---|---|
| Normal | `M_Elev_ChamberGlass` → **기각**, `M_Cab_Bulb` 채택 | 따뜻한 아이보리, 비금속, 발광 없음 — 차분하고 "온전한" 인상. `ChamberGlass`는 `blend_method=BLEND, alpha=0.15`로 **거의 투명** — 고체 구슬에 쓰면 유령처럼 비쳐 보여 즉시 기각 | `ChamberGlass`(투명), `M_Elev_LampEmissive`(빨간 발광 — "정상"에 위험색은 부적절) |
| Absorber | `M_Elev_CavityDark` | 거의 검정(0.007), 무광(roughness 0.95), 발광 0 — 이 씬에서 이미 실제 공동(디스펜서, 천장 캐비티)에 쓰이는 재질이라 "없음/빨아들임"과 의미가 정확히 겹친다 | `M_Elev_DarkIron`(금속성이 강해 "공허"보다 "쇠"로 읽힘) |
| Proliferator | `M_Elev_SirenLens` | 따뜻한 호박색, 발광 강도 0.8 — "경고/주의 끄는" 인상, 이미 사이렌 렌즈로 쓰여 "위협의 신호"라는 의미가 재사용된다 | `M_Elev_GaugeFill`(주황 발광 — 이미 전력 게이지·스핀 게이지 전용으로 과다 사용 중이라 재사용하면 "이게 게이지인가 구슬인가" 혼선 우려로 회피) |

## 8. 부가 작업 — Task #14 SpinGauge 6개 월드 좌표 재배치

Phase 1 보고서(`<scratchpad>/BLENDER_EXPORT_REPORT.md` §6)에서 발견만 하고 미루었던
버그를 이번 세션에서 Task #14로 받아 수정했다.

**원인**: `SOCKET_ElevPanel`이 3축 균일 1.37724배 스케일을 갖는데(회전 없음),
2026-08-09 스핀 게이지 배치 세션이 **월드 좌표로 잰 목표값을 그대로 로컬
location/scale에 대입**해 이 배율을 누락했다.

**수정식** (parent translation `(0, 2.19, -0.37653)`, scale `1.37724` 균일):

```
새 로컬 location = (기존값 − parent_translation) / parent_scale
새 로컬 scale    = 기존값 / parent_scale
```

`기존값`은 원래 월드 목표로 의도됐던 바로 그 숫자이므로 그대로 재사용했다 —
목표 위치를 새로 정하지 않고 **변환만 바로잡았다.**

| 오브젝트 | 이전 월드 X | 이전 월드 Z | 새 월드 X | 새 월드 Z |
|---|---|---|---|---|
| Housing | 0.708~1.259 | 1.930~1.999 | **0.514~0.914** | **1.675~1.725** |
| Cell_0 | 0.730~0.826 | 2.006~2.061 | 0.530~0.600 | 1.730~1.770 |
| Cell_4 | 1.088~1.184 | 2.006~2.061 | 0.790~0.860 | 1.730~1.770 |

`SM_LeverBay` 월드 bbox 대비 확인:

```
LeverBay   X [0.50325, 0.92468]   Z 상단 1.94881
Housing    X [0.514,   0.914  ]   Z 상단 1.725     ✓ 둘 다 안쪽
```

수정 후 **하우징이 베이 X 범위 안에 완전히 들어가고, Z 상단도 베이 천장보다
223mm 아래**다 — 수정 전(베이 밖으로 X 334mm·Z 50mm 초과)에서 완전히 해소됐다.

**남는 사소한 것 (이번 범위 밖, 참고만)**: 하우징 하단(Z 1.675)이 레버 손잡이
윗면(`SM_Lever_Handle.003` 실측 Z 1.6958)보다 20mm 낮다 — 원래 설계 문서
(`BLENDER_SPIN_GAUGE.md`) 자체의 수치 정의가 "하우징 중심 위치"와 "여유 공간
하단"을 같은 1.7000으로 섞어 쓴 데서 오는 미세한 기존 오차다. 이번 Task는
"부모 스케일 버그"만 다뤘으므로 이 20mm는 고치지 않았다. 셀 5개끼리도 설계
수치상 인접 셀이 5mm씩 겹친다(피치 0.065 vs 폭 0.070) — 이것도 원래 설계값의
산술이지 이번에 만든 문제가 아니다.

## 9. 실패했거나 못 한 것 — 숨기지 않는다

1. **텍스처 밀도 축을 차별화하지 않았다** (§3). 지시가 「블렌더로 되는 세 축」 중
   하나로 꼽았는데 손대지 않고 넘어갔다 — 세그먼트 밀도를 의도적으로 다르게
   해 저해상도 자체를 하나의 신호로 쓰는 후속 작업이 가능하다.
2. **흡수체 실루엣이 5회 만에 통과했다** (§4) — 지시된 "최대 3회"를 문자 그대로
   지키지 못했다. 3회 실패 후 구조를 바꾸라는 지시를 따른 것이라고 판단했지만,
   더 보수적으로는 v3에서 멈추고 판단을 넘겼어야 한다고 볼 수도 있다. 5장
   렌더 전부 스크래치패드에 남겨 뒀으니 재검토할 수 있다.
3. **구슬이 실제 챔버 안에 들어갔을 때의 클리어런스를 검증하지 못했다** (§1.3).
   과거 이 시스템이 "너무 큰 구슬"로 챔버 후면을 뚫은 사고 이력이 있는데, 이번
   150.8mm 구슬은 절대 크기로 그때와 비슷한 영역이다. 챔버 안 최종 배치 전
   `WindowChamberDepth`·`SoulStandoff` 기준으로 반드시 재확인이 필요하다.
4. **Unity 임포트 후 실제 화면 검증은 못 했다** (Unity MCP 금지). 실루엣 판정은
   블렌더 정면 직교 렌더 기준이고, 실제 게임 카메라 각도·조명·재질 임포트 결과는
   다를 수 있다.
5. **정면 축 규약(-Y)이 실제 챔버 설치 방향과 맞는지 미확인**이다 (§2 서두). 안
   맞으면 오브젝트 전체를 Y축 기준으로 회전만 하면 되고 재모델링은 필요 없다.
6. Task #17 export는 계획대로 됐지만, **SOCKET_ElevPanel이 껍데기(Empty)로만
   들어가고 그 하위 계층 구조가 Unity 재임포트 시 기존 프리팹과 어떻게
   맞물리는지는 검증하지 못했다** (Phase 1 보고서에서도 같은 한계를 적었다).
