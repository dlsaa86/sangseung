프레임 하나가 180프레임 평균을 124 KB 밀어올린다. "게임 루프가 매 프레임 할당하는가"는
평균이 답할 수 없는 질문이다. 중앙값·95%·최대·**0 B 프레임 비율**로 바꿨다.

또 게임 쪽 MonoBehaviour를 **전부 끈 대조군**을 추가해, 남은 바닥이 우리 코드인지
에디터·URP인지 분리했다.

#### 결과 (중앙값 기준, Apple M5 / Metal / 에디터 Play)

| 조건 | GC/프레임 중앙 |
|---|---|
| 전체 | **12,615 B** |
| IMGUI 디버그 HUD 끔 | 10,411 B |
| 게임 뷰 컴포넌트까지 전부 끔 | **8,773 B** |

- **HUD 기여: 2,204 B** (이전 약 127,000 B → **98% 감소**)
- 나머지 게임 코드 기여: 1,638 B
- **게임 코드 합계: 3,842 B** (이전 약 134,000 B → **97% 감소**)
- **에디터·URP 바닥 8,773 B는 우리 코드가 아니다** — 게임 컴포넌트를 전부 꺼도 남고,
  중앙값과 95%가 같다(상태와 무관하게 일정하다).

#### 고친 다섯 곳

| 위치 | 무엇이 문제였나 |
|---|---|
| `RouletteHud` | `OnGUI`는 프레임당 Layout·Repaint로 **최소 2회** 불린다. 그 안에서 상태 문자열을 매번 조립했고 `GUILayout`은 호출마다 레이아웃 항목을 할당한다 → 고정 Rect + 재사용 `GUIContent` + 변경 시에만 재조립 |
| `CrosshairInteractor` | `GetComponentsInParent`(**복수형**)가 호출마다 배열을 만든다. 매 프레임 스피어캐스트 히트마다 불려 프레임당 최대 16개 → 단수형 인터페이스 조회 |
| `InstrumentPanelView` | 매 프레임 라벨 3줄을 보간 문자열로 조립 → `StringBuilder` + TMP의 `SetText(StringBuilder)` 오버로드(중간 string 없음) + 표시값 변경 시에만 |
| `RouletteInteractionBridge` | 매 프레임 프롬프트 3개를 조립 → 상태 키가 바뀔 때만 |
| `RiskStateView` | 매 프레임 `Explain()`(List + `string.Join`) → 위험 요인 구성이 바뀔 때만 |

#### 아직 남은 것

- **`TECH_SPEC.md` §13의 "프레임당 0 B" 는 에디터에서 확인할 수 없다.** 에디터·URP 바닥
  8.8 KB가 게임 코드 기여분(3.8 KB)보다 크기 때문이다. 0 B 주장은 **플레이어 빌드
  프로파일링**으로만 가능하다.
- 게임 코드에 남은 3.8 KB의 세부 출처는 특정하지 않았다. 남은 후보는 IMGUI 자체의
  이벤트 처리(디버그 HUD를 실제 UI로 교체하면 사라진다)와 뷰의 `MaterialPropertyBlock` 경로다.
- **최악 프레임 스파이크는 그대로다** (중앙 0.91 ms 대비 최악 130 ms, 143배).
  원인 미확정 — GC 수집으로 추정되나 확인하지 않았다.

## 프레임 스파이크 원인 규명 (커밋 예정)

직전 보고의 "최악 프레임 130 ms, 중앙의 143배 / 원인 미확정"을 계측으로 좁혔다.
가설을 세우고 **하나씩 반증**하는 순서로 진행했다.

### 계측 설계

프레임타임만으로는 "왜 느렸는가"를 절대 알 수 없다. 그래서 느린 프레임과 **같은 프레임의**
정황을 함께 찍었다: GC 세대별 누적 수집 횟수, TMP 동적 아틀라스 글리프 수·텍스처 장수,
연출 단계, 스핀 입력 여부.

### 가설 1 — TMP 동적 아틀라스 확장 → **반증**

`NanumGothic SDF`가 `atlasPopulationMode: Dynamic`이고, 폰트 에셋이 이전 커밋들에서
플레이 모드 중 계속 수정돼 있었다(런타임에 글리프가 추가된 흔적). 가장 유력해 보였다.

측정 결과 **모든 스파이크에서 글리프 증가 0**:

| 실행 | 기준 초과 프레임 | 그중 글리프 증가 |
|---|---:|---:|
| 1회차 | 37개 | **0개** |
| 2회차 | 33개 | **0개** |
| 3회차 | 31개 | **0개** |

글리프 수도 측정 전후 171개로 동일. 아틀라스도 2장 그대로. **기각.**

### 가설 2 — 연출(캐스케이드 재생)이 무겁다 → **반증**

시드 12를 고정해 **같은 연쇄를 세 번** 재생하며 컴포넌트를 하나씩 껐다.

| 조건 | 프레임 | 중앙 | 최악 | 스파이크 | 최대 할당/프레임 |
|---|---:|---:|---:|---:|---:|
| ① 전부 켬 | 3,978 | 1.14 ms | 4.6 ms | **0개** | 0.1 MB |
| ② HUD 끔 | 3,915 | 1.17 ms | 2.6 ms | **0개** | 0.1 MB |
| ③ HUD + 표식 끔 | 3,833 | 1.18 ms | 8.1 ms | **0개** | 0.1 MB |

**통제된 재생에서는 스파이크가 아예 나오지 않는다.** 최대 단일 프레임 할당도 0.1 MB로,
문제 구간에서 보이던 5~18 MB와 두 자릿수 배 차이다. 연출·표식·HUD 어느 쪽도 아니다.

정착 상태(스핀 이후 300프레임)도 마찬가지로 깨끗하다 — 최악 1.63 ms, 중앙의 1.4배.

### 가설 3 — 에디터 환경의 GC 수집 → **확인됨**

게임 코드를 **전부 끄고** 60초를 재는 대조군에서도 스파이크가 그대로 나온다:

| 대조군(게임 코드 전부 끔) | 값 |
|---|---|
| 프레임타임 중앙 | 1.26 ms |
| **최악** | **45.6 ms** (중앙의 36배) |
| 최대 단일 프레임 할당 | **3.15 MB** |
| 최악 프레임 2개의 정황 | 할당은 baseline(8,773 B)인데 **gen0/1/2 동시 수집** |

가장 느린 프레임들이 "할당은 평소와 같은데 전 세대 GC가 돌았다"는 형태다. 이건 정의상
**GC 일시정지**다. 게임 코드가 하나도 안 돌고 있어도 발생한다.

### 결론

1. **프레임 스파이크는 게임 루프가 만들지 않는다.** 같은 연쇄를 통제 재현하면 0개다.
2. **가장 큰 스파이크는 전 세대(gen2) GC 일시정지다.** 게임 코드를 전부 꺼도 45 ms가 나온다.
3. **TMP 동적 아틀라스는 원인이 아니다.** 모든 스파이크에서 글리프 증가 0.
4. 다만 **우리 코드도 GC 빈도에 기여한다** — 프레임당 약 11 KB를 꾸준히 할당하므로 gen0을
   계속 채운다. 그중 8.8 KB는 게임 코드를 전부 꺼도 남는 에디터·URP 바닥이고,
   게임 코드 몫은 약 2.5 KB(대부분 IMGUI 디버그 HUD)다.

### 남은 정직한 한계

- 처음 관측한 **131 ms 스파이크는 통제 재현으로 되살리지 못했다.** 그 구간은 앞선 측정
  단계들이 힙을 충분히 어지럽힌 뒤였고, 누적된 힙에 대한 gen2 수집으로 보는 것이 가장
  일관된 설명이다. 그러나 "그 한 프레임이 확실히 gen2 때문이었다"를 단정하지는 않는다.
- **에디터 측정으로는 여기까지가 한계다.** GC 일시정지의 실제 크기와 빈도는 빌드에서
  다르고, 에디터 바닥(8.8 KB/프레임)이 게임 몫(2.5 KB)보다 크기 때문에
  "0 B 목표" 판정도 빌드에서만 가능하다. → 기준 PC(Windows) 확보 시 재측정 필요.

### 조치

원인이 게임 코드가 아니므로 **코드는 고치지 않았다.** 근거 없는 최적화를 넣는 대신
계측 하네스를 저장소에 남겼다(`Ascend/Measure Hero Slice Performance`) — 다음 세션이
빌드에서 같은 구분(게임 코드 / 에디터 바닥 / GC 일시정지)을 바로 다시 낼 수 있다.

## IMGUI 디버그 HUD → UGUI 실제 UI 교체

### 무엇을 화면에 남길 것인가부터 정했다

단순 이식이 아니다. 옛 IMGUI HUD는 층·전력·요구·게이지·계약·잔류·스핀·결과판 미러를
한 화면에 전부 쏟았고, 그건 두 조항을 어긴다:

- `MASTER_PRD.md` §6.1 — "한 화면에 모든 숫자를 동시에 띄우지 않는다.
  큰 배수 하나, 현재 캐스케이드 단계, 핵심 발동 원인을 우선 강조한다."
- `VISUAL_SPEC.md` §5 — "상호작용물은 현대적 HUD처럼 떠 보이면 안 된다."

그래서 역할을 나눴다. **화면에는 공간이 담을 수 없는 것만 남긴다.**

| 정보 | 어디서 말하는가 |
|---|---|
| 전력·요구·임계점·스핀·잔류·계약 | **벽면 계기판** (`InstrumentPanelView`) — 이미 있다 |
| 지금 무엇을 할 수 있는가 | **조준 프롬프트** (`CrosshairView`) — 이미 있다 |
| 지금 무엇 때문에 터졌는가 | 화면: 연쇄 단계 + 원인 한 줄 (연출 중에만) |
| 층이 왜 그렇게 끝났는가 | 화면: 사고 기록기 요약 + 재현 시드 |
| 다음 행동 안내 | 화면: 아래 가운데 **한 줄** (숫자 없음) |

### 신규

| 파일 | 역할 |
|---|---|
| `UI/GameHudView.cs` | 게임 화면 UI. 안내 한 줄 / 연쇄 배너 / 층 결과. CanvasGroup 페이드 |
| `UI/DebugPanelView.cs` | **분리된** 디버그 패널. **기본 꺼짐**([F1]로 토글) |
| `UI/RouletteHud.cs` | **삭제** — 씬에서도 제거 |

디버그 패널을 분리하고 기본으로 끈 이유: `VISUAL_SPEC.md` §5에서 "보조 수치와 디버그 정보"는
6순위(맨 끝)다. 옛 HUD는 이걸 게임 정보와 한 덩어리로 묶고 기본 ON이라 캡처·성능 양쪽에
상시로 끼어들었다.

시드 입력에 `TMP_InputField`를 쓰지 않는다. 1인칭이 커서를 잠그고 있어 입력 필드에 포커스를
주려면 잠금을 풀어야 하고, 그러면 조사하려던 상태가 바뀐다. Input System의 `onTextInput`으로
직접 받으면 커서를 건드리지 않는다.

### 결과 — 프레임당 GC 할당

정착 상태(스핀 이후 300프레임) 중앙값 기준:

| 조건 | GC/프레임 |
|---|---:|
| 화면 UI 켬 | **8,853 B** |
| 화면 UI 끔 | 8,853 B |
| 게임 코드 전부 끔(에디터 바닥) | 8,773 B |

- **화면 UI 기여: 0 B/프레임** (옛 IMGUI HUD는 2,204 B, 최초에는 약 127,000 B)
- **게임 코드 전체: 80 B/프레임** (최초 약 134,000 B → **99.9% 감소**)

`SetText(StringBuilder)` + 표시값이 바뀔 때만 재조립 + CanvasGroup 알파(활성 토글 아님)로
정착 상태에서 문자열·메시 재생성이 아예 일어나지 않는다.

**단, "유휴(계약 선택 대기)" 구간 수치는 이번에도 신뢰할 수 없다** — Play 진입 직후라
TMP가 새 UI의 한글 글리프를 처음 래스터라이즈하고 에디터가 가장 시끄러운 시점이다.
실제로 그 구간은 "UI 끔"이 "UI 켬"보다 할당이 **더 크게** 나왔다(불가능한 결과).
정착 상태 수치만 근거로 쓴다.

### 검증

- PlayMode **43 PASS / 0 FAIL / 콘솔 오류 0** — UI 항목 8개 신규
  (존재·기본 꺼짐·안내 표시·연쇄 즉시 표시·연출 후 사라짐·결과 표시·안내 사라짐)
- EditMode 54 PASS / 0 FAIL (회귀 없음)
- 캡처 `09_screen_ui_hint`, `10_screen_ui_cascade` 추가

### 검증 중에 잡은 결함 2건

1. **연쇄 배너가 페이드로 떴다.** 첫 단계의 정화 맥동이 0.55초인데 페이드가 0.17초를 먹어
   "무엇 때문에 터졌는가"를 읽을 시간을 그만큼 깎았다. → **뜰 때는 즉시, 사라질 때만 페이드.**
2. **검증이 프레임 수로 기다리고 있었다.** 에디터가 1000fps로 도는 바람에 "30프레임 대기"가
   0.03초가 되어 페이드가 끝나기 전에 검사했다. → 시간 기준 대기(`WaitSeconds`)로 교체.

### 캡처 경로에 대한 주의

**Screen Space Overlay 캔버스는 카메라의 RenderTexture에 렌더되지 않는다.** 고정 시점
캡처 세트(전용 카메라 → RT, 1920×1080)에는 화면 UI가 절대 나오지 않는다.
그래서 UI 확인용으로 `ScreenCapture` 경로를 따로 뒀고, 해상도가 게임 뷰 크기라
**고정 비교 세트가 아니다**(매니페스트에도 그렇게 적었다).

## 과수확 레버를 "대표 장면"으로 — Gate C 마감

Gate C에 남아 있던 마지막 항목. `MASTER_PRD.md` §7이 이 레버를 대표 장면으로 지정했는데
캡처에서는 그냥 회색 상자였다.

### 발견 1 — `Unlocked` 이벤트에 구독자가 없었다

`InteractableOverharvestLever.Unlocked`를 만들어두고 **아무도 듣지 않았다.** 그래서
`VISUAL_SPEC.md` §7의 "해제 순간 조명, 소리, 기계 반응이 집중된다"가 통째로 빠져 있었다.
덮개만 조용히 열리고 끝났다.

`View/OverharvestUnlockEffect.cs` 신설 — 해제 순간 네 채널이 동시에:

| 채널 | 내용 |
|---|---|
| 조명 | 전용 스폿이 확 켜졌다가(0.18s) 낮게 가라앉는다(0.9s) |
| 기계 | 실내등이 45% 어두워졌다 돌아온다 — 전력을 이쪽으로 뺏긴 것처럼 |
| 소리 | 걸쇠 풀리는 둔탁한 소리 + 올라가는 톤 (절차 생성, 외부 에셋 없음) |
| 진동 | 레버 덩어리가 짧게 떨린다 |

그리고 풀린 **동안** 경고 띠가 계속 발광한다 — 잠김/해제가 정지 화면에서도 구분되도록.

### 발견 2 — 덮개가 손잡이를 가린 적이 없다 (캡처가 잡음)

주석은 "덮개가 닫히면 손잡이가 실제로 가려진다"고 주장했지만 캡처에서 잠김 상태인데
손잡이가 그대로 보였다. 깊이를 계산해 보니 **덮개가 손잡이보다 0.22m 뒤**에 있었다.

두 번 고쳤다:
1. 덮개를 앞으로 옮겼다 → 이번엔 0.022m 만 앞이라 손잡이가 덮개를 **관통**했다.
2. 하우징을 오목한 함(깊이 0.52)으로 만들고 손잡이를 그 안에 넣었다.

## 캡처 리그 1차 실행에서 드러난 결함

매니페스트가 실패를 그대로 기록하도록 만든 것이 즉시 값을 했다.

```
09_risk_warning   Warning — 과적 218/130 / 실제 단계 Stable
10_risk_critical  Critical — 실제 단계 Stable / 점수 0.0
```

과적 218/130인데 위험 단계가 Stable이었다. 원인: `RunSession.AddWeight`가
`_baseWeight`만 바꾸고 **이미 만들어진 층에는 전파되지 않았다.** 층은 생성 시점의

## 독립 QA 감사 (Gate H) — 내 판정을 뒤집었다

읽기 전용 독립 감사가 `P2-Gate A~H`를 재판정했다. 결과: **A만 완전 통과, B·C·E·F 부분,
D·G·H 미통과.** 내가 보고한 "A~D 통과"는 과했고, 근거는 감사가 제시했다.

### 확인하고 인정한 결함

**1. `TestNoDoubleSpendOfSurplus`가 항상 참인 빈 테스트였다**

기대값을 계산해 놓고 버린 채 `Money > 잉여총합 + 1000` 하나만 단언했다.
무적재 런에서는 `Money = Σ max(0, 잉여 − 소비) ≤ Σ 잉여`가 **수학적으로 항상 성립**하므로
그 조건은 어떤 시드에서도 참이 될 수 없다. 결정적으로 — **고치기 전 버그
(`Money += ExcessPower`)에서도 `Money == 잉여총합`이라 그대로 통과한다.**
내가 고친 이중 지급의 유일한 회귀 방지선인데 방지선이 아니었다.

근본 원인은 기대값을 `FloorResult.FloorsAscended`(클램프 **전**)로 계산한 것이었다.
정산은 클램프 **후** 값으로 이뤄지므로 애초에 비교가 성립하지 않았다.

→ `RunSession.FloorAscent` 신설. 정산한 쪽이 클램프 후 층수와 실제 지급액을 기록한다.
테스트는 층마다 `지급액 == max(0, 잉여 − 추가층×60)`을 정확히 단언하고,
추가 층을 사고도 잉여 전액을 받았으면 이중 지급으로 잡는다.
**다층 상승이 한 번도 안 나오면 실패로 처리하는 자기 검사**도 넣었다 — 이 테스트가
다시 빈 테스트가 되는 것을 막는다.

**2. 10층 완주를 단언하는 헤드리스 테스트가 0건이었다**

"10층 진행" 테스트 7개가 전부 실패 런을 `continue`로 건너뛰거나 상한만 확인해서,
**모든 시드가 1층에서 죽어도 전원 통과**했다. Gate B의 헤드리스 근거는 없었고
완주 증거는 PlayMode 로그 한 줄뿐이었다.

→ `고정 시드 3개 이상이 10층을 완주한다` 신설 (9시드 중 3회 요구).
→ `적재하고도 10층을 완주할 수 있다` 신설. **이게 더 중요하다** — 무적재 완주만으로는
   Gate B와 Gate C가 충돌한다. "완주 가능한 유일한 방법이 아무것도 싣지 않는 것"이면
   적재 시스템은 순수한 함정이다. 둘 다 통과했다.

**3. 무게 전파 수정이 여전히 재발 가능했다**

`RunSession.Loadout`이 public이라 `Loadout.Add()`가 갱신을 타지 않았고,
**내 캡처 리그가 정확히 그 경로를 쓰고 있었다**(`TenFloorCaptureRig.cs:120`).
즉 내가 잡았다고 보고한 결함과 같은 부류가 열려 있었다.

→ 호출부마다 갱신을 기억하게 하는 대신 **변경 자체가 알리도록** 뒤집었다.
   `BuildLoadout.Changed` 이벤트를 `Add`/`Remove`/`Clear`/`TakeDeparting`에 붙이고
   `RunSession`이 구독해 현재 층을 갱신한다. 회귀 테스트 `적재 직접 변경도 현재 층에
   반영된다`가 싣고 내리는 양방향을 확인한다.

**4. 내가 프레임당 GC 할당을 새로 넣었다**

`BuildFigureView.LateUpdate`가 매 프레임 `floor.Plan.Floor + "/" + floor.Phase + …`
문자열을 만들었다. `object[]` 배열 + enum 박싱 + `ToString()`이 프레임마다 발생한다.
**바로 위 세 줄에 "GC를 134KB→3.8KB로 끌어내린 작업을 되돌리는 짓"이라고 써놓고
캐시 키 자체를 문자열로 만들었다.**

→ 정수 비트 패킹으로 교체(`층<<12 | 단계<<8 | 후보<<4 | 적재`).
   문 프롬프트도 상태 키가 바뀔 때만 짓는다. `RiskStateView`·`Camera.main` 탐색도
   1회 시도 후 표식을 세워 매 프레임 전역 탐색을 막았다.
   같은 저장소의 `RouletteInteractionBridge`·`GameHudView`가 쓰던 규약을 따랐다.

**5. 자동 조종의 항상 참인 단언과 실패→성공 전환**

- `과수확을 안 당기면 추가 스핀이 소비되지 않는다` — `sawOverharvest`가
  `useOverharvest` 블록 안에서만 대입되므로 보수 정책에서 **정의상 항상 참**이었고,
  `ExtraSpinsTaken`을 한 번도 읽지 않았다. → 층마다 실제 값을 누적해 단언한다.
- `if (!overharvest.CanInteract) { sawOverharvest = true; }` — 손잡이를 **잡을 수 없을 때**
  플래그를 세워 뒤쪽 "당길 수 있다" 단언을 통과시켰다. 실패를 성공으로 뒤집는 코드였다.
  → 제거. 공격 정책에 `과수확이 실제로 추가 스핀을 소비했다`를 추가로 요구한다.

## GC 수정 후 재측정 — 기대와 다른 결과를 그대로 적는다

`BuildFigureView`의 프레임당 문자열 할당을 제거한 뒤 같은 하네스로 다시 쟀다.

| 항목 | 제거 전 | 제거 후 |
|---|---|---|
| 판정 스핀당 | 14.2 µs | **11.8 µs** |
| 유휴 GC 중앙 (전부 켬) | 10,693 B | 10,443 B |
| 유휴 GC 중앙 (게임 컴포넌트 끔) | 9,055 B | 8,805 B |
| **게임 코드 기여분** | 1,638 B | **1,638 B — 변화 없음** |
| 재생 중 최악 프레임 | 31.94 ms (중앙의 3.8배) | **17.36 ms (2.1배)** |

**문자열 키 제거가 GC 중앙값을 낮추지 못했다.** 두 계층이 나란히 250 B씩 줄었는데

수정 자체는 옳다 — 매 프레임 `object[]` + 박싱 + `ToString()`은 없어야 할 패턴이고
저장소의 다른 뷰가 이미 정수 키를 쓴다. 다만 **"GC를 줄였다"고 주장할 근거는 없다.**
남은 게임 코드 1.6 KB/프레임의 출처는 아직 특정하지 못했고, 프로파일러 수준의
분해가 필요하다. `TECH_SPEC.md` §13의 "프레임당 0 B" 목표는 여전히 미달이다.

개선된 것은 **재생 중 최악 프레임**이다(31.94 → 17.36 ms). 단 각 1회 측정이라
노이즈와 구분되지 않는다.

## 캡처가 잡아낸 결함 두 건 더

### 층수 표시등이 좌우 반전으로 찍혔다

`06_risk_stable`에서 출입구 위 표시등이 "1 / 10"의 거울상으로 나왔다. 씬 라벨이 아니라
**내가 만든 `FloorIndicatorView`**다.

원인: `holder.transform.localRotation`을 `AddComponent<TextMeshPro>()` **앞에서** 설정했다.
TMP 를 붙이면 `RectTransform`이 새로 달리면서 기존 `Transform`을 교체하고, 그때 회전이
유실된다. 글자가 +Z(벽 안쪽)를 향해 실내에서는 뒷면이 보였다.

### 내가 만든 회귀 (중대) — 수정함

`CompleteFloor`는 `DisembarkAt`을 `CreateCurrentFloor()`보다 **먼저** 부른다.
그 시점의 `_current`는 아직 **방금 확정된 그 층**이다. 무게 전파를 고치면서
`TakeDeparting`이 `Changed`를 쏘게 만들었으므로, 하차가
`OnLoadoutChanged → _current.RefreshLoad()`를 타고 **끝난 층의 `_carriedWeight`와
`_requiredPower`를 사후에 바꿨다.**

`AccidentRecorder`는 한 프레임 뒤에 기록한다. 그래서 승객이 내린 층의
`FloorRecord.CarriedWeight`·`RequiredPower`·`Overloaded`가 **그 층에 실제로 적용된
값이 아니었고**, 같은 기록 안의 `result.RequiredPower`와도 어긋났다.

원래 감사가 지적한 "기록과 실제가 다르다"를 **방향만 뒤집어 재발**시킨 것이다.

→ `OnLoadoutChanged`에 `_current.Result != null`이면 건너뛰는 가드를 넣었다.
   회귀 테스트 `하차가 확정된 층의 숫자를 바꾸지 않는다`가 층마다 확정 전후 값을 비교한다.

**교훈**: 캐시를 갱신하는 코드는 "언제 갱신하지 **말아야** 하는가"를 함께 정해야 한다.
갱신 조건만 넓히면 반대편에서 같은 종류의 오염이 생긴다.

## 계약 조건을 계기판에 넣으려다 세 번 실패했다

## 이분 탐색의 순서 교란 — 감사자가 옳았다

앞선 감사가 지적했다. ①②③을 항상 같은 순서로만 재면 "③에서 스파이크가 크다"와

순서를 뒤집어 한 번 더 쟀다.

| 구성 | 정방향 최악 | 반전 최악 |
|---|---|---|
| ① 전부 켬 | **161.8 ms** (첫 측정) | 31.3 ms (마지막) |
| ② HUD 끔 | 17.1 ms | 17.2 ms |
| ③ HUD + 표식 끔 | 17.1 ms (마지막) | 17.0 ms (첫 측정) |

②·③은 실행 위치와 무관하게 17 ms에 붙어 있다. 161.8 ms는 **재현되지 않았다** —
첫 측정 구간의 워밍업이다. 수거 카운터도 여섯 구간 전부 g0/g1 0회로, 스파이크가
GC와 함께 움직이지 않았다.

결정적인 것은 대조군이다. **게임 코드를 전부 끄고 60초를 잰 최악 프레임이 39.7 ms**로,
HUD를 켠 재현 최악(31.3 ms)보다 크다. 그 프레임에는 g0/g1/g2 수거가 1회씩 걸려 있다.

→ 재생 구간의 스파이크는 게임 코드에 귀속되지 않는다. 에디터 Play 모드의 잡음 바닥이
이미 그보다 크다. 이전 기록의 "③ 140 ms 스파이크"는 **구성이 아니라 첫 측정 위치**를
본 것이었고, 그 귀속은 틀렸다.

빌드 성능 판정은 여전히 미결이다 — `TECH_SPEC` §13에 따라 에디터 수치로 선언하지 않는다.

데이터 프로파일 7종, 승객 반응, 사운드, 풀링·성능 프로브, 방어 테스트.

## 왜 사건 버스를 먼저 만들었나

텔레메트리·사운드·승객 반응·위험 연출은 **같은 사건에 반응해야 하는데 서로 다른 층위에
산다** — 앞의 둘은 순수 C# 판정 옆에, 뒤의 둘은 MonoBehaviour 연출 옆에.
각자 `SpinResolution` 을 다시 해석하게 두면 "정화가 일어났다"의 정의가 네 벌 생기고,
그중 하나만 고쳐도 채널 사이가 어긋난다. PRD §9 마지막 문장이 정확히 그것을 금지한다.

버스는 **런이 소유한다.** 정적 싱글턴으로 두면 런을 재시작했을 때 옛 구독자가 살아남아
두 런의 사건이 한 텔레메트리 파일에 섞인다. 런이 죽으면 버스도 죽는다.
구독자 하나가 던진 예외는 다른 채널을 죽이지 않는다 — 사운드가 실패해도 기록은 남아야 한다.

Notion MASTER PRD 원문을 직접 열어 두 가지가 진행 문서와 다르다는 것을 확인했다.
