## 1. 게임플레이 통과 기준

- [ ] 개발자 조작 없이 **1층부터 10층까지** 플레이 가능
- [ ] 계약 · 스핀 · 정화 · 직선 · 연결 · 캐스케이드 · 잔류 · 승객/부품 · 과수확 · 성공/실패가 **연결됨**
- [ ] 감각적 위험 상태가 **실제 게임 상태와 동기화**됨
- [ ] 사고 기록기가 런 데이터를 정확히 출력함
- [ ] 진행 불가 상태 없음
- [ ] **서로 다른 두 빌드가 실제 판정 규칙과 의사결정을 바꾼다**

## 2. UX / 가독성 통과 기준

플레이테스터가 **설명 없이** 다음을 말할 수 있어야 한다.

- [ ] 무엇을 모으면 상승하는가
- [ ] 저항체가 왜 위험한가
- [ ] 3개 정화와 패턴 보너스의 차이
- [ ] 현재 계약의 이익과 대가
- [ ] 지금 통과 가능한가
- [ ] 지금 왜 위험한가
- [ ] **과수확이 무엇을 걸고 무엇을 얻는가**
- [ ] 직전 성공 또는 실패의 원인

### 2.1 관전자 기준 (무음 영상)

- [ ] 지금 통과 가능한가?
- [ ] 지금 위험한가?
- [ ] 왜 한 번 더 돌리려 하는가?
- [ ] 무엇이 연쇄를 만들었는가?
- [ ] 어떤 승객·부품이 핵심인가?
- [ ] 왜 성공하거나 실패했는가?

### 2.2 접근성

- [ ] 작은 버튼 정밀 조준·빠른 클릭을 요구하지 않는다
- [ ] 카메라 셰이크 강도 · 사이렌 음량 · 섬광 강도가 **옵션으로 분리**돼 있다
- [ ] 색이 없어도(흑백·색각 차이) 심볼이 구분된다

## 3. 감정 · 방송성 통과 기준

**10분 플레이 안에** 다음이 최소 한 번씩 발생해야 한다.

- [ ] 플레이어가 선택을 **입 밖으로 설명하게 되는** 계약 선택
- [ ] 요구 전력 달성 후 **멈출지 더 갈지 고민하는 순간** (1회 이상)
- [ ] **3연쇄 이상의 예상 밖 연쇄** (1회 이상)
- [ ] 위험 단계가 한 단계 상승하는 **감각적 사건** (별도 설명 없이 인지됨)
- [ ] 성공 · 비명 · 웃음 · 후회 중 **관찰 가능한 반응** 1회 이상
- [ ] 사고 기록이 한 런의 이야기를 요약함

## 4. 기술 통과 기준

### 4.1 테스트

- [ ] **핵심 EditMode 테스트 전부 통과** (15항목, [GAMEPLAY_SPEC.md](GAMEPLAY_SPEC.md) §10)
- [ ] PlayMode 7항목 통과
- [ ] **동일 시드 재현** 확인
- [ ] 캐스케이드 무한 루프 없음 (하드 캡 20 동작 확인)
- [ ] **실패한 테스트를 삭제·무시·조건부 스킵으로 숨기지 않는다**
- [ ] 테스트 실패 상태로 다음 Phase에 진입하지 않는다

### 4.2 성능

| 항목 | 기준 |
|---|---|
| 기준 해상도 | **1920×1080** |
| 목표 | **90 FPS** |
| 하드 플로어 | 캐스케이드 20회 + Critical 연출 중에도 **지속적으로 60 FPS 미만 하락 없음** |
| GC Alloc | 워밍업 이후 일반 이동·대기·룰렛 회전·위험 피드백의 매 프레임 루프 **0 B 목표** |
| 비정기 할당 | 씬 로드·런 시작·결과 보고서 생성은 허용하되 **측정하고 기록** |
| 메모리 | 10층 연속 플레이에서 **지속 누적 없음** |
| 프레임 스파이크 | 룰렛 판정 중 **체감 가능한 스파이크 없음** (ms 임계값 미명시) |

> 🔴 **`TargetHardwareProfile`이 미지정이면 성능 완료를 선언할 수 없다.** (기술 부록 08 명시)
> 현재 미지정 상태다.

⚠ 08 내부 모순 — §3.2는 목표 90 FPS, §20.3 완료선은 평균 60 FPS.
MASTER PRD가 성능 합격선의 최종 권한이다.

### 4.3 구조

- [ ] 게임 규칙과 프레젠테이션 분리
- [ ] 핵심 판정이 **순수 C# 또는 EditMode 테스트 가능한 서비스**로 구현됨
- [ ] **씬 오브젝트 이름 검색 금지**
- [ ] 의존성은 Inspector 참조 또는 명시적 초기화로 주입
- [ ] **필수 참조 누락 시 개발 빌드에서 즉시 명확한 오류** (조용히 실패 금지)
- [ ] 풀링 · 압축 Preset · 품질 프로파일 적용
- [ ] 반복 `Instantiate/Destroy` · LINQ · 문자열 결합 · 매 프레임 컴포넌트 검색 없음
- [ ] 하드코딩된 수치가 설정 자산으로 옮겨짐

## 5. 비주얼 통과 기준

### 5.1 필수 고정 캡처 세트 9종

동일한 해상도 · FOV · 카메라 위치 · 시간대 · 품질 프리셋을 사용한다.

1. 엘리베이터 입구에서 본 전체 내부
2. 룰렛 정면
3. 계약 선택 상태
4. Stable 상태
5. Critical 상태
6. 과수확 레버 접근 순간
7. 5연쇄 이상
8. 사고 직후와 사고 기록기
9. 승객 4명과 화물이 최대 적재된 상태

> ⚠ **추가 필요**: 실행 레버 · 과수확 · 전력 탱크 **3물체가 함께 들어오는 지점**이 없다.

### 5.2 평가 루브릭 (각 1~5점)

1. 한눈에 목적이 읽히는가?
2. 상호작용물이 배경과 구분되는가?
3. **정상 영혼·흡수체·증식체를 1초 안에 구분하는가?**
4. 정화와 캐스케이드 원인을 따라갈 수 있는가?
5. Stable과 Critical의 감정 차이가 명확한가?
6. 저폴리 실루엣과 재질 언어가 일관적인가?
7. 빛과 VFX가 판독성을 해치지 않는가?
8. **화면이 카지노 슬롯머신 또는 장식적 스팀펑크로 보이지 않는가?**
9. 한 장의 스크린샷이 게임의 고유성을 전달하는가?
10. 스트리머 영상에서 중요한 상태가 축소 화면으로도 읽히는가?

### 5.3 🔴 통과 조건

- [ ] **판독성 항목 평균 4.0 이상**
- [ ] **스타일 일관성 평균 4.0 이상**
- [ ] **단일 항목 2점 이하 없음**
- [ ] **이전 버전보다 개선되지 않은 수정은 채택하지 않는다**

> 심볼 판독(#3)과 전력 판독(#4)이 2점인 한 평균 4.0은 **산술적으로 불가능하다.**
> 셸을 아무리 고쳐도 2.6대에서 멈춘다. → [CURRENT_STATE.md](CURRENT_STATE.md) §6.3

### 5.4 추가 확인

- [ ] Stable · Critical · Collapse가 명확히 구분됨
- [ ] 결과판 심볼 3종이 1초 내 구분됨 (**흑백에서도**)
- [ ] 캐스케이드의 원인이 읽힘
- [ ] 사용자 승인 대기 항목이 **교체 가능한 상태로 유지**됨

## 8. 반복 개선 프로토콜 (확정)

1. 구현 에이전트가 기능과 1차 프레젠테이션을 완성한다
2. 자동 테스트와 프로파일링을 실행한다
3. 고정 캡처와 짧은 플레이 영상을 생성한다
4. **비주얼 평가 역할이 레퍼런스와 현재 결과를 블라인드 비교**한다
5. 문제를 `형태 · 배치 · 조명 · 재질 · VFX · 사운드 · 정보` 중 하나로 분류한다
6. **가장 영향이 큰 1~3개 문제만** 수정한다
7. 같은 조건으로 다시 캡처하고 점수를 비교한다
8. 최소 2회 반복하며, 통과 기준을 만족하면 멈춘다

> **측정 가능한 차이 없이 무작정 반복하지 않는다.**
> 각 반복은 변경 이유 · 기대 효과 · 실제 결과를 기록한다 → [ITERATION_LOG.md](ITERATION_LOG.md)

### 8.1 반복 상한

**같은 층위에서 3번 실패한 항목은 4번째를 시도하지 않는다.**
필요한 것은 노력이 아니라 **구조 변경이나 배치 결정**이다.

## 10. 독립 검증 규칙 (뒤집히지 않음)

| 규칙 | 내용 |
|---|---|
| 1 | **구현자가 자기 결과를 최종 평가하지 않는다.** 평가자는 어느 쪽이 새 빌드인지 모른 채 본다 |
| 2 | **직전 승인 빌드보다 나빠지면 채택하지 않는다** |
| 3 | 테스트·캡처·성능 기준을 통과하지 않은 기능은 완료로 선언하지 않는다 |
| 4 | 실패와 미완료를 숨기지 않고 재현 절차와 원인을 기록한다 |
| 5 | `CONNECTED → VERIFIED` 승격은 독립 검증을 거친다 — 시각은 `VISUAL_VERDICT.md`의 ACCEPT, 로직은 독립 감사자 |

**베이스라인은 기기에 종속된다.** OS·GPU·그래픽 API가 다르면 렌더 결과가 비트 단위로 다르다.
기기를 옮기면 그 기기에서 베이스라인을 새로 세운다 (`machineFingerprint`가 강제).

> 🔴 현재 `Captures/baseline.txt`가 **없다** = 승인된 베이스라인이 부재하다.

## 11. 문제 보고 형식 (필수)

모든 문제는 다음 형식으로 작성한다.

```
문제 ID / 담당 영역 / 우선순위(P0~P3) / 문제 위치 / 현재 상태 / 목표 상태
문제의 원인 / 구체적인 수정 방법 / 수정 담당자 / 검증 방법 / 완료 조건
관련 Notion 페이지 / 이전 반복 대비 변화
```

### 11.1 🚫 금지된 지시

> 더 멋있게 · 더 디테일하게 · 더 무섭게 · 퀄리티를 높여라 ·
> 자연스럽게 수정 · AAA처럼 제작 · 알아서 개선 · 완성도를 올려라

**모든 지시는 관찰 가능하고 검증 가능한 형태로 작성한다.**

## 12. 첫 플레이테스트 판정 기준 (후보 — 8개 중 5개 이상 통과)

- 3개 정화를 자가 설명 **80% 이상**
- 계약 위험·보상 이해 **70% 이상**
- 추가 스핀 선택률 **20~70%**
- 특정 계약 선택률이 **80%로 고착되지 않음**
- 중도 포기 **20% 미만**

> 기술 부록 08: *"이 문서의 수치는 밸런스 확정값이 아니라 **검증 가능한 초기값**이다."*

## 13. 플레이테스트 관찰 항목

- 설명 없이 첫 레버를 찾는 시간
- 첫 3개 정화 이해 시간
- 계약 선택에 걸린 시간과 이유
- **요구 전력 달성 후 고민 시간**
- 과수확 선택률
- 플레이어가 실패 원인을 설명할 수 있는지
- 관전자가 무음 영상에서 상태를 설명할 수 있는지
- 멀미 · 섬광 · 사이렌 피로도

**플레이 중 규칙을 옆에서 설명하지 않는다.**

## 14. 패스별 게이트 (프로젝트 고유)

`docs/TOPDOWN_MASTER_BACKLOG.md`의 네 패스와 대응한다.

| 패스 | 완료 기준 | 요구 증거 |
|---|---|---|
| Pass 1 | 소유 Required가 최소 `SKELETON`·`VISIBLE` | 상태 바 |
| Pass 2 | 소유 Required가 최소 `CONNECTED` | + 끊긴 증거 경로 |
| Pass 3 | `PASS3_GATED` 28항목 `VERIFIED` + 시각 `ACCEPT` | + 캡처 세트 · 독립 평가 · 콘솔 오류 |
| Pass 4 | **모든** Required `VERIFIED` | + 전체 테스트 · 빌드 · 10층 증거 · 미커밋 0 |

패스와 무관하게 늘 지켜야 하는 것 셋 — **컴파일 통과 · 분류 모순 없음 · 진행 문서·브랜치.**

**미룬 요구는 반드시 적는다.** 게이트 완화가 곧 "사라진 요구사항"이 되지 않게.
