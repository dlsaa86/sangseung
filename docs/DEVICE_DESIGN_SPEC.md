# 2. 엘리베이터 공간 고정 조건

## 2.1 출입구는 한 개만 존재한다

- **Notion 근거**: 06 §8 「현재 엘리베이터 설계 고정 조건」 — "출입구는 한 개만 존재한다.", "NPC가 배치되는 벽에는 출입구가 없다."
- **현재 구현**: BackWall(z = +1.60)에만 개구부가 있다. 씬 오브젝트는 `BackWall_Left` / `BackWall_Right` / `BackWall_Lintel` 3분할 구조이며, 좌우 벽은 `WallL` / `WallR`, 상하는 `Ceiling` / `Floor`다.
- **검증 결과**: 씬 오브젝트 이름 전수 조회에서 **`FrontWall`에 해당하는 오브젝트가 존재하지 않는다.** z = −1.70 면이 비어 있다는 메인 에이전트의 관찰이 확인된다.
- **차이**: 출입구 개수는 조건을 만족한다. 그러나 **z = −1.70 면이 열려 있다.** 플레이어 시작 위치가 (0.55, 0, −0.85)이므로 **뒤를 돌면 벽이 없는 방향을 본다.**
  - 폐쇄 공간감(`VISUAL_SPEC.md` §1 "공간은 좁고 높고 기능적이어야 한다")과 충돌한다.
  - Notion 06 §8 "NPC가 배치되는 벽에는 출입구가 없다"를 적용하려면 **승객이 설 벽면이 실제로 존재해야 한다.**
  - **판정: 미충족.** z = −1.70 면에 벽 모듈이 필요하다. (구현은 씬 소유자 담당 — 이 문서는 요구만 기록한다)

## 2.2 층수 표시기 위치

- **Notion 근거**: 06 §8 — "층수 표시기는 출입구 위 또는 옆에 배치한다."
- **레퍼런스 근거**: `docs/references/elevator/d5cfa65b-*.png` — 가위문 **바로 위**에 상하 화살표를 동반한 2자리 숫자 표시기("02")가 있다.
- **현재 구현**: `FloorLabel`, `DoorSign` 오브젝트가 존재한다. 정확한 좌표는 본 문서 범위에서 미확인 → **자료 부족**.
- **차이**: 오브젝트는 존재하나 "출입구 위 또는 옆" 조건 충족 여부는 좌표 확인 필요.

## 2.3 수확 장치와 레버의 배치

- **Notion 근거**: 06 §8 — "수확 결과 슬롯 계기판과 엔진 가동 레버는 **출입구 오른쪽 구석**에 배치하되, 1인칭 시점에서 자연스럽게 발견되고 접근 가능한 시선 높이와 거리를 확보한다."
- **현재 구현**: 통관·결과판이 **x = −1.45 (좌측 벽)**, 전력 탱크가 **x = +1.34 (우측, 문 근처)**, 과수확 레버가 **(0.55, 1.32, 1.36)**.
- **차이**: **불일치 가능성 있음.** "출입구 오른쪽"의 기준(밖에서 들여다볼 때 vs 안에서 문을 볼 때)이 Notion에 명시돼 있지 않다.
  - 플레이어가 문(+z)을 향해 서면 통관은 **왼쪽**, 문을 등지면 **오른쪽**이 된다.
  - **판정: 자료 부족.** 기준 방향을 확정해야 판정 가능하다 → `NotionSyncReport.md` 승인 항목으로 이관.
- **부수 관찰 (확인 필요)**: `OverharvestLever`가 (0.55, 1.32, **1.36**)이고 출입구 개구부는 BackWall(z = +1.60)의 x ≈ 0.15~1.15 구간이다. 레버 x = 0.55는 **개구부 x 범위 안**이고 z = 1.36은 문에서 **0.24m 앞**이다. 산술상 레버가 출입구 통로를 가로막는 위치일 수 있다. Notion 06 §8은 "승객과 화물이 탑승해도 플레이어가 **출입구·레버·계기판에 접근할 수 있는 보행 동선**을 남긴다"를 요구한다. → **씬 소유자 확인 필요.**

## 2.4 내부 사다리와 천장 해치

- **Notion 근거**: 06 §8 — "내부 확장용 사다리는 존재하지만 **기본 상태에서는 상단 금속 해치가 닫혀 있다.**", "2층·3층 확장 시 닫힌 해치 모듈을 열린 해치와 상부 바닥 모듈로 교체한다."
- **현재 구현**: 씬 전수 조회 결과 **사다리·해치에 해당하는 오브젝트가 존재하지 않는다.**
- **차이**: **미구현.** 단, 이는 확장 대비 항목이며 `CURRENT_PHASE.md`의 현재 범위(1~10층 플레이 가능)에 포함되지 않는다. **지금 만들 필요는 없고, 벽 모듈을 설계할 때 사다리 자리를 남겨두면 된다.**

## 2.5 승객 보행 동선과 화물 공간

- **Notion 근거**: 06 §8 — "승객과 화물이 탑승해도 플레이어가 출입구·레버·계기판에 접근할 수 있는 보행 동선을 남긴다." / 03번 — "엘리베이터는 좁고 압박감 있어야 하지만 플레이어, 승객과 화물이 서로 끼어 핵심 장치에 접근하지 못하는 상황은 만들지 않는다."
- **현재 구현**: `PassengerAnchor`, `CandidateAnchor` 앵커가 존재한다. 좌석·벤치 오브젝트는 없다(Notion 모듈 목록의 `ELV_NPC_Bench` 미구현).
- **차이**: 앵커는 있으나 **최대 적재 시 동선이 확보되는지는 미검증**. `MASTER_PRD.md` §11 필수 캡처 세트의 "승객과 화물 최대 적재 상태" 캡처로 검증해야 한다. → **자료 부족.**

## 2.6 외부 공간 깊이

- **Notion 근거**: 「3D 리소스 타겟」 §4 — "**문 밖 깊이 3~5m의 작은 무대로 제한한다.**" 구성 = 바닥·벽·천장 모듈 / 막힌 통로 또는 외부 문 / 천장 조명과 층 번호 / 배관·전선·상자·폐기물.
- **레퍼런스 근거**: `8d1de57c-*.png` — 문 밖에 카트 1대, 벽등, 안쪽 끝의 문 하나가 보이는 짧은 복도. Notion의 "짧은 탐색용 무대" 의도와 일치한다.
- **현재 구현**: `Lobby`, `LobbyBack`, `LobbyFloor`. z = 3.2 ~ 4.6 → **깊이 1.4m**.
- **차이**: **미달.** Notion 하한 3m의 절반에 못 미친다. 1.4m는 "문 밖을 내다본다"는 감각을 만들기 어렵고, 03번이 요구하는 "문이 열리며 1인칭으로 확인할 수 있는 짧은 공간과 장면 제시"가 성립하지 않는다.
  - 단, 03번은 "문 밖 공간이 **핵심 룰렛 루프를 과도하게 지연시키지 않는다**"도 함께 요구하므로 **3m가 하한이자 적정선**으로 읽힌다.

## 2.7 상호작용 규격

- **Notion 근거**: 08 §15.2 — "상호작용 가능 거리 권장값: **2.5m**", "대상 콜라이더는 시각 모델보다 **약간 크게** 설정", "조준 시 외곽선 또는 발광", "화면 중앙에 행동 문구 표시", "**클릭 1회로 실행. 길게 누르기 금지. 작은 버튼 정밀 조준 금지.**"

# 3. 세 통관과 결과판

## 3.1 통관 배치와 결과판 대응

- **Notion 근거**: 01번 「초기 장치 구조」 — "투명 수직 통관 3개가 나란히 배치된다.", "각 통관은 한 번의 스핀에서 영혼 3개를 포획한다.", "최종 결과는 3열 × 3행, 총 9칸이다.", "결과판은 파이프 내부에 세로로 쌓인 구슬 3개씩으로 보이거나, 바로 옆 판독창에 3×3으로 명확히 표시한다."
- **Notion 근거**: 08 §7.1 — "인덱스는 `row * 3 + column` 방식으로 통일한다.", "**시각적으로는 각 통관이 한 열을 담당한다.**"
- **저장소 근거**: `VISUAL_SPEC.md` §3 — "세 개의 수직 통관이 나란히 배치된다. 각 통관은 결과판의 한 열과 대응한다."
- **현재 구현**: `TubesRoot` 아래 `Tube_0/1/2`, 각 통관에 `Cell_0/1/2`. 통관은 z축으로 −0.50 / 0.00 / +0.50 배치, 셀은 y축으로 2.00 / 1.60 / 1.20.
- **차이 (판독)**: **구조는 일치한다.** 통관 = 열, 셀 = 행 대응이 성립한다.
- **차이 (비례)**: 열 간격 0.50m, 행 간격 0.40m로 **3×3이 정사각 격자가 아니다.** Notion 07번은 "정지된 결과판에서 1초 안에 세 심볼을 구분", "**같은 저항체 3개를 빠르게 셀 수 있는가**"를 요구한다. 비정사각 격자는 **대각선 직선 패턴의 판독을 특히 어렵게 만든다** — 대각선이 45°가 아니라 약 38.7°(atan 0.40/0.50)로 기울기 때문이다.
  - **권고(구현 지시 아님)**: 대각선 판정 VFX를 넣을 때 이 각도 차이를 전제로 설계하거나, 행·열 간격을 맞추는 안을 씬 소유자가 검토한다.

## 3.2 🚨 통관별 정지 버튼 — 폐기 구조가 씬에 남아 있다

- 그레이박스 단계에서는 문제되지 않으나, **실제 3D 모듈 에셋을 제작할 때는 Notion 명명 규칙을 쓰는 편이 좋다** — 06 §8이 모듈 교체(닫힌 해치 → 열린 해치)를 전제하고, 접두사 규칙이 교체 대상 식별을 쉽게 한다.
- **미구현 4종**(사다리 벽, 해치 2종, 벤치)은 모두 현재 범위 밖이거나 선택 사항이다.

# 8. 레퍼런스 이미지가 보여주는 장치 형태와의 충돌
