## D-20260731-03 — 다층 상승이 최종 층과 빌드 보상 층을 건너뛰지 못한다

- 상태: Accepted
- 결정일: 2026-07-31
- 결정자: 구현 에이전트 (`agent/phase2-full-prototype`)
- 관련 문서/파일: `Run/RunSession.cs` `ClampAscent`, `Run/AscendResult.cs`, `Spin/FloorPlan.cs`
- 결정: `PowerBand.MultiFloor` 이상에서 발생하는 자동 추가 층 상승을 유지하되,
  **최종 층**과 **`OffersBuildReward` 층** 앞에서 멈추도록 자른다. 그 외의 건너뛰기는
  높은 임계점의 보상으로 남긴다. 추가 층에 쓴 전력은 돈으로 중복 지급하지 않는다.
- 이유: 헤드리스 5시드 실측에서 1→2→3→4→**8**→9로 뛰어 5·6·7층을 통째로 건너뛰었고,
  5개 중 2개 시드가 **최종 층 10층을 치르지 않고** 완주했다. 도달 층은 `highest=13`으로
  10층 건물의 범위를 벗어났다. 가르치는 층과 종합 시험을 건너뛴 완주는 "1층부터 10층까지
  연속 진행"의 증거가 되지 못한다. 빌드 보상 층은 승객·부품을 얻는 유일한 지점이라
  건너뛰면 Gate C가 성립조차 하지 않는다.
- 대안: (1) 자동 다층 상승 제거 — `PowerBand`의 "추가 층 상승" 의미가 사라진다. 기각.
  (2) 잉여 배분을 플레이어 선택으로 승격(`AscendResult.AllocateSurplus`의 원래 설계) —
  이번 범위에서 선택 UI를 하나 더 늘리면 확정/과수확의 대등함이 흐려진다. 후속으로 남긴다.
- 영향: 최종 층은 항상 플레이된다. `HighestFloorReached`가 `LastFloor`를 넘지 않는다.
  같은 전력으로 층과 돈을 동시에 받던 이중 지급이 사라져 고득점 런의 소지금이 줄어든다.
- 후속 작업: 잉여 배분을 플레이어 선택으로 올릴지 Phase 3에서 재검토.

## D-20260731-04 (결정 요청 — 미확정)

**`PowerBand.Jettison`(요구 전력의 70~89%)이 실제로 무엇을 빼앗는가.**

열거형은 "승객·화물 포기 또는 큰 대가"로 선언돼 있으나 구현이 없다.
`RequiresJettison`은 실패 문자열을 만드는 데만 쓰인다(`AscendResult.cs:66`).
게임이 "화물 포기"라고 말한 뒤 아무 일도 일어나지 않고, 적재가 없는 런에서는
문구가 뜻을 잃는다. 독립 시각 감사가 이 모순을 잡아냈다.

정해야 할 것:
  1. 무엇을 버리는가 — 무작위 1개 / 가장 무거운 것 / 플레이어 선택
  2. 적재가 없을 때의 대체 대가 — 소지금 차감 / 다음 층 요구 증가 / 없음
  3. 승객을 버릴 수 있는가 — `MASTER_PRD` 의 톤과 직결된다

## 2026-08-02 — 오디오 5항목 Deferred 재분류를 **되돌린다** (독립 감사 지적)

앞선 항목에서 `UP-AUD-01`~`05` 를 `Required` → `Deferred` 로 내렸다. **독립 감사가
그것이 틀렸다고 판정했고, 파일로 확인한 결과 맞다.** 되돌린다.

**왜 틀렸나 — 셋 다 확인했다.**

1. **백로그 §0.2 의 `Deferred` 정의에 맞지 않는다.** 정의는 「PRD §4.2 **명시적 제외**,
   또는 다른 문서에만 있고 PRD 필수 범위에 없는 확장」인데 **`MASTER_PRD.md` §4.2 에
   오디오가 없다.** 오히려 §9 는 「각 상태는 조명, **사운드**, 기계 진동에서 동기화되어야
   한다. 특정 감각 채널 하나에만 의존하지 않는다」이고, §14 Phase 4 통과 조건은
   「무음 영상과 **오디오만 듣는 테스트** 모두에서 위험 단계 변화를 구분할 수 있다」이다.
2. **사용자 지시가 매핑되는 문서가 다르다.** 「그래픽에만 집중한다」는 **세션 범위**
   지시이고 그 자리는 `CURRENT_PHASE.md` 다. `CURRENT_PHASE` §3 이 제외한 것도
   「**최종** 사운드와 음악」이지 사운드 자체가 아니다. 제품 범위(`Deferred`)를 건드릴
   근거가 아니었다.
3. **경계가 자의적이었다.** 같은 오디오 요구인 `UP-RISK-05`(사이렌·응력음, PRD §9) ·
   `UP-RISK-06`(파열음) · `UP-NPC-04`(비언어 음성)는 Required 로 남겨 두었다.
   같은 근거로 내릴 수 있는 것을 안 내렸다면 그 근거가 근거가 아니다.

**그리고 실제로 게이트를 하나 새로 만들었다.** `:185` 의 `PASS3_GATED:` 인덱스 줄이
여전히 `UP-AUD-01..05` 를 가리켜, 검증기가 `[4] C10b — PASS3_GATED 가 Required 에 없는
ID 를 가리킨다` 로 **새로 실패했다.** 게이트를 풀려던 변경이 게이트를 만들었다.

**남는 문제는 그대로다** — 「Required 인데 이번 세션 범위 밖」을 표현할 상태값이 없다.
`Deferred` 로 표현하면 제품 요구를 지우게 되고, `Required` 로 두면 이번 세션에 손대지
않기로 한 항목이 Pass 4 를 막는다. **상태값을 늘리는 쪽이 요구를 지우는 쪽보다 싸다** —
사용자 결정 사항으로 올린다.

**교훈**: 게이트가 안 닫힌다는 이유로 **분류를 손대는 것**은 거의 항상 잘못된 층위다.
막는 것이 요구인지 기록인지 먼저 갈랐어야 했다. 오늘 낡은 기록을 다섯 번 고친 것은
옳았고, 이건 그것과 다른 종류였다.

## 2026-08-02 — 게이트의 발동 시점을 바꾼다 (사용자 승인)

**결정**: Stop 훅이 매 턴 검사하는 대상을 **「프로토타입 전체가 끝났는가」에서
「이 배치가 주장한 것을 실제로 했는가」로** 바꾼다. 규칙은 하나도 지우지 않는다.

**왜**: 훅이 매 턴 「Pass 4 전부 VERIFIED + 시각 ACCEPT + Required 40건 승격」을 요구했다.
그 셋은 여러 시간·여러 라운드가 걸리는 일이다. 그래서 **한 축을 제대로 고친 턴에도 예외 없이
「미완료」가 나왔고**, 그 판정을 해명하는 데 턴이 소모됐다. 진짜 진전과 정체가 구분되지 않았다.

오늘 하루의 예 — 현창 3×3 이 G-SLOT 미달을 7장에서 2장으로 줄이고 띠를 24장 전부 0 으로
만들었으며, 12라운드짜리 「슬롯머신」 지적을 구조로 닫았다. 그 턴의 판정도 「미완료」였다.
**규칙이 품질을 만들었고 게이트의 발동 시점이 낭비를 만들었다.**

**어떻게**: `tools/verify-topdown.ps1` 에 `-Batch` 스위치를 넣었다.

| | 무인자 실행 (최종 판정) | `-Batch` (Stop 훅) |
|---|---|---|
| C2 Pass 4 전부 VERIFIED | **막는다** | 미룬다 |
| C10 시각 ACCEPT | **막는다** | 미룬다 |
| C10b Pass 4 지정 항목 | **막는다** | 미룬다 |
| 컴파일·자체검증 신선도 | 막는다 | **막는다** |
| 트리 청결 · 분류 모순 | 막는다 | **막는다** |
| PlayMode 결과 · 진행 문서 | 막는다 | **막는다** |

가르는 기준은 하나다 — **한 배치가 혼자 충족시킬 수 있는가.** 승격은 독립 감사의 일이고
시각 판정은 평가자의 일이다. 구현자가 그것들을 스스로 만들면 그건 검증이 아니다(6조).

**요구를 지우지 않는다.** 미룬 항목은 전부 「지금은 막지 않는다」 절에 **ID 와 함께 출력된다.**
이 저장소가 이미 적어 둔 원칙이다 — *「게이트 완화가 곧 사라진 요구사항이 되지 않게 하기 위한 것」*.
최종 판정은 여전히 무인자 실행이고, 그 자는 아무것도 미루지 않는다.

**남기는 것 — 오늘 실제로 값을 했다.**

- 구현자 자기 승격 금지 → 독립 감사가 낡은 차단 기록 10건을 찾았다
- 증거 신선도 → 콘솔 오류 3건을 숨기던 낡은 로그를 잡았다
- 씬 단독 소유 → 소유자가 내 「유리가 원인」 전제를 렌더러 소거로 반증했다.

- 한 배치 한 축 → G-SLOT 7→2 를 현창 덕분이라고 **귀속**할 수 있었다
- 3회 실패하면 층위를 올린다 → 17차가 `07`·`14`·`17` 을 「더 노력하라」가 아니라
  **결정 철회**로 올렸다

# D-20260802-10 — 2단 통합 레버와 남은 스핀 정산

> **사용자 확정.** Notion `MASTER PRD` · `99. 결정 로그` · `T-05` 에 반영돼 있고
> 이 절은 그 **동결 스냅샷**이다. 문구를 새로 쓰지 않고 Notion `T-05` 를 그대로 옮겼다 —
> 두 문서가 「비슷한 말」이 아니라 **같은 문장**이어야 다음 대조가 성립한다
> (`UP-DOC-01` 에서 배운 것).

## 무엇이 바뀌었나

| | 이전 | 지금 |
|---|---|---|
| 레버 | 일반 실행 레버 + 과수확 레버 **둘** | **2단 기계식 통합 레버 하나** |
| 전력 확정 | 과수확 레버와 같은 벽의 별개 조작 | **별도 브레이크로 유지** |
| 남은 스핀 | 확정하면 **사라짐** | **운행 효율 정산**으로 환산 |

## 왜 통합이 안전한가 — 국면이 배타적이다

`FloorSession.Spin()` 은 `Phase == Spinning` 에서만, `PushYourLuck()` 은
`Phase == Decision` 에서만 유효하다. **같은 순간에 둘 다 유효한 경우가 없다.**
그래서 하나의 레버가 국면에 따라 다른 일을 해도 모호성이 생기지 않는다.

그리고 사용자가 제시한 레퍼런스 이미지에 **레버가 하나뿐이다** — 붉은 손잡이 레버
하나 위에 `OVERHARVEST / EXTREME DANGER` 라벨, 아래에 `EXECUTE ↓`.
둘로 나눠 둔 직전 상태가 오히려 레퍼런스와 달랐다.

`VISUAL_SPEC` §7 「과수확 레버가 일반 실행 레버와 혼동되지 않아야 한다」는
**더 잘** 지켜진다 — 둘을 나란히 두는 것보다 **하나가 상태를 바꾸는 것**이 눈에 띈다.
덮개·레일 연출은 `OverharvestUnlockEffect` 가 이미 구현해 두었다.

## 정산이 없으면 선택이 하나뿐이다

이것이 이 결정의 핵심 근거다. 남은 스핀의 가치가 0 이면 「지금 멈춘다」가
전략이 되지 못하고 **항상 과수확이 옳다.** 선택지가 하나뿐인 것은 선택지가 아니다.

정산이 붙으면 두 값이 실제로 겨룬다 — 안전(남은 스핀 × 5%, 확정) vs
과수확(그 권리를 버리고 더 큰 초과 전력).

**정산은 스핀이 아니다.** 캐스케이드·임계점·승객·부품 효과를 발동하지 않는다.
발동하면 「안 돌린 스핀」이 「돌린 스핀」과 같아져 위 대비가 사라지고,
결정론 재현에도 새 난수 소비처가 생긴다.

그리고 **전력에 더하지 않고 돈으로만 준다.** 전력에 더하면 임계점을 넘겨
상승 층수를 바꿔 버린다.

## 2026-08-09 — 보드는 3×3 을 유지한다 (확장은 최후 수단)

**결정**: 통관 보드를 **3×3 으로 유지한다.** 3×5(클로버핏 배열)·5×5 확장과
「승객이 통관 개수를 늘려 준다」는 안은 **채택하지 않고 최후 수단으로 내린다.**

**사용자 원문**: 「우선은 3×3 배열로만 가자. 더 어렵게 할 방법들이 있는지 보고,
정 어려우면 배열을 늘려서 어렵게 만들든가 해야지. 근데 3×3은 뭔가 좀 쉬워서
도파민이 적을 것 같기도 하다.」

### 무엇을 대신 하는가

사용자의 걱정은 **둘이고 서로 다른 문제**다. 섞으면 틀린 처방이 나온다.

- 「쉽다」 = **난이도** — 요구 곡선·가중치·잔류 손실 등으로 올린다
- 「도파민이 적다」 = **보상의 진폭과 예측 불가능성** — 어렵게 만든다고 해결되지 않는다.
  어렵기만 하고 짜릿하지 않으면 오히려 최악이다

칸을 늘리지 않고 경우의 수를 늘리는 **정공법은 심볼 종류를 늘리는 것**이다
(현재 3종: 정상 영혼·흡수체·증식체). 보드 확장과 달리 **현창 3×3 기하를 건드리지
않으므로** 블렌더 메시 1개와 규칙 배선만으로 끝난다 — 이것이 결정적인 비용 차이다.

### 승객이 확장을 준다는 안을 왜 내렸나

사용자가 스스로 함정을 짚었다 — 「그러면 무조건 그 승객을 태우려고 하게 되려나」.
확장이 순수 이득이면 그 승객은 **선택이 아니라 세금**이 되고, 빌드 다양성이 오히려
줄어든다. **항상 정답인 선택지는 선택지가 아니다.**
지금 과수확이 「전력 100% 넘기면 그냥 됨」(`FloorSession.cs:470`)인 것과 **같은 종류의
문제**이며, 같은 원리로 함께 풀어야 한다.

### 다시 검토하는 조건

3×3 안에서의 난이도·진폭 조정을 **먼저 소진한 뒤에만** 확장을 재검토한다.
발동 조건은 `docs/runtime/PLAN_BUILD_DEPENDENCY.md` §C-3 의 3단 계단에 적는다.

## D-2026-08-09 — 전력·돈 구조 재설계 (사용자 결정)

### 확정된 게임 흐름

```
룰렛을 돌린다 → 전력을 얻는다
  → 제한된 스핀 안에 다음 층 요구 전력을 맞추면 산다
  → 못 맞추면 엘리베이터 추락
  → 맞춰도 자동으로 안 올라간다. 엘리베이터 옆 버튼이 활성화되고, 눌러야 올라간다
  → 요구보다 초과해 넣으면 한 번에 여러 층을 올라간다
  → 스킵된 층수만큼 돈이 추가로 나온다
  → 스핀 횟수를 남겨도 돈이 된다
```

### 1. 전력 게이지판 → LED 디스플레이

퍼센트 채움 막대와 0~100 눈금을 버린다. 전력은 **상한 없는 수치**이므로 퍼센트가
성립하지 않는다. 클로버핏의 슬롯머신 위 다용도 텍스트 패널과 같은 역할.
블렌더 구현은 `AD59_LEDPANEL`, 제거된 것은 `SM_Gauge_Fill`·`SM_Gauge_Labels`.

### 2. 정보 배치 — 세 곳에 나눠 싣는다

| 어디 | 무엇 |
|---|---|
| **아래 LED 디스플레이** (`SM_Gauge_Screen`) | **한 번의 조작마다 얻은 전력** (총량 아님) |
| **2D UI · 플레이어 시점 정중앙 하단** | 현재 얻은 **전력 총량** |
| **상승 버튼 위** | 그 조작에 요구되는 **전력 요구량** |

⚠ 디스플레이가 총량을 말하지 않는다는 점이 핵심이다. 세 값을 한 판에 몰면
「무엇이 방금 일어났는가」와 「내가 지금 어디쯤인가」가 뭉개진다.

### 3. 잉여 전력은 택일이 아니다 — 층 **그리고** 돈

직전 규칙은 `SurplusUse` 셋(Ascend / Money / Bank) 중 **하나**라, 층을 오르면 돈이 0
이었다. 이제 층을 오르면 **건너뛴 층수 × 4골드**가 함께 나온다.

**층당 4골드** (2026-08-09 사용자 결정: 「층당 4골드로 하자 우선은」).

⚠ **전력을 돈으로 바꾼 것이 아니다.** 층에 쓴 전력(층당 60)은 그대로 소모되고,
지급 근거는 **층수**다. 그래서 「추가 층 전력이 돈으로 중복 지급되지 않는다」가
그대로 성립한다. 둘을 헷갈리면 「층을 건너뛴다」가 「전력을 환전한다」가 된다.
구현: `AscendResult.DefaultGoldPerSkippedFloor` · `AllocateSurplus`.

### 4. 과수확은 **보류** (삭제 아님)

「일단 과수확 컨셉은 제거하자 이건 보류해야 할 것 같으니까」.
104개 파일 1,300곳을 지우는 대신 단일 관문
(`FloorSession.IsOverharvestUnlocked`)에 스위치를 걸었다 —
`PrototypeFeatures.Overharvest = false`. 되살리는 비용은 그 한 줄이다.

### 5. 신규 기계는 **그레이박스 초안까지만**
